{% comment %} templates/includes/_overlay_sheet.html — Map fly-out sheet primitive (SNOW-486). Extracts the byte-identical outer wrapper shared by the favourite and report map sheets (public/partials/_favourites_surface.html, public/partials/_report_surface.html) — an empty container the owning JS (favourites.js / report.js) fills via ``innerHTML`` or an HTMX swap, never server-rendered with static children. Hide idiom: the HTML5 ``hidden`` ATTRIBUTE (not a class) — matches every other map-internal/JS-driven overlay (#home-intro, #map-help-overlay). Carries a bare ``data-overlay`` (no ``data-overlay-hide`` override, so static/js/overlays.js's shared handler uses its attribute default) so a "×" rendered inside it — anywhere, including content injected later by JS — is caught by the shared delegated dismiss handler without each sheet's own JS needing to bind a document click listener for it. Required context: id — DOM id on the sheet container (e.g. "favourite-sheet"). aria_label — Translated label text for the sheet's aria-label. Optional context: static — Bool; default False. When True renders inline (no ``hidden``, no ``fixed`` positioning, no z-index) — used only by the component library, mirroring _toast.html's "static" convention. A slot of placeholder text is shown in place of the real (JS-injected) content so the empty shell isn't invisible in the panel. scroll_body — Bool; default False. Ignored when ``static``. SNOW-645 review — see the "Bounded height" section below for the defect this exists to fix. False (favourites, report): the SHEET ITSELF scrolls as one block (``overflow-y-auto`` on this element) — the safe default for a body injected wholesale by JS (favourites.js / report.js), which this partial has no visibility into and so cannot carve a scroll region out of. True (the "Manage downloads" sheet): this element becomes a flex column with its OWN overflow hidden instead (``flex flex-col overflow-hidden``, no scrolling here) — the caller's own body is then responsible for marking ONE of its children as the scroll region (``flex-1 overflow-y-auto min-h-0``) while its header and footer stay pinned as ordinary, non-growing flex children. See _map_downloads_sheet.html for the concrete shape. ``tabindex="-1"`` (SNOW-538) makes the container a programmatic focus target without putting it in the tab order: favourites.js and report.js both call ``sheet.focus()`` on open, which was silently a no-op on a non-focusable div. It matters now that the favourite create form no longer focuses its name input on open — focusing that input raised the on-screen keyboard before the user had placed the pin. TWO LAYOUTS, ONE SHEET — AND THE DIFFERENCE IS DELIBERATE (SNOW-658). Below the ``sm`` breakpoint (640px) this sheet spans the full width of the viewport and docks to its bottom edge, so an open panel covers the map. At ``sm`` and above it is width-capped (``sm:w-96``) and inset into the bottom-right corner, so the map stays usable beside it. That is not an accident of the classes: a docked sheet is the right shape on a phone (the list is what is being read, there is no room to show it beside anything, and the bottom edge is where the thumb is), and on a desktop the map is large enough that covering it would be the loss. Both layouts are bounded and scroll internally — see "Bounded height" below. Expect "the panel fills the screen on mobile" as a REPORT rather than a bug: it is the intended behaviour, documented in §3.7 of docs/map-page-functional-spec.md so it does not get "fixed". On mobile the sheet is inset from the viewport edges rather than full-bleed, via the shared --map-edge-inset-* tokens (src/css/main.css) — the same distance the map control roundels use, so the sheet's edges line up with the stack above it, on notched devices too. Being inset on all sides, it also takes a full border and radius rather than the top-only pair it used while it was docked flush to the bottom. Desktop placement is refined in JS (SNOW-658). The ``sm:`` classes below put the sheet in a fixed viewport corner, which knows nothing about the season scrubber along the foot of the map or the roundel column at its right edge — so on desktop the sheet opened over both. Each map caller (map_sheet.js's ``open()`` for the favourite and report sheets, map_downloads_manager.js's own ``open()`` for downloads) hands the element to ``window.pwaOverlayBounds.positionSheet`` (static/js/map_overlay_bounds.js), which measures the room those leave and writes ``bottom`` / ``right`` / ``max-height`` inline. The classes here stay as the fallback: they are what renders with JS unavailable, below the ``sm`` breakpoint (where nothing is written and any previous inline value is cleared), and for the ``static`` component-library render, which is inline rather than fixed and is never positioned. Bounded height (SNOW-645 review). This element used to set no max-height at all — content-driven height on a ``fixed``, bottom-docked box, so a sheet with enough content (the "Manage downloads" sheet with ten-plus areas is what surfaced it) grows UPWARD past the top of the viewport, pushing its own header off-screen entirely with nothing to stop it. All three consumers can hit this, not just downloads — the fix lives here, once, rather than in the one sheet that happened to prove it. ``max-h-[calc(100dvh-var(--map-edge-inset-top)-var(--map-edge-inset-bottom))]`` bounds it to "the room between the top of the screen and this sheet's own bottom inset" — the SAME arbitrary-value-plus-token idiom this file already uses for its position (``bottom-[var(--map-edge-inset-bottom)]`` etc.), not a new mechanism. ``dvh``, not ``vh``: on mobile ``vh`` ignores the browser chrome and would let the sheet run underneath it — the same bug in a subtler form. {% endcomment %}
