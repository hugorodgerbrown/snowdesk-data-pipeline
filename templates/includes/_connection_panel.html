SNOW-921: one surface, not three -------------------------------- It used to say things and do one thing. Everything a user might actually want to DO about the network lived somewhere else: the "Offline mode" switch was in the account dropdown (and so existed only for signed-in readers), and the on-device debug trace was a separate floating pill at the bottom-left of the page with no relationship to the header at all. The symbol that reports the network now opens the one place you act on it. So the panel is two halves with a rule between them: * ABOVE — what is true. The summary line, the per-state explanation. Read, not operated. Unchanged from SNOW-748 bar the wording of its own header. * BELOW — what you can do. "Offline mode", the debug-log entry, and the way back to the network. In the order the account menu already established: the row you open the menu to OPERATE first, then the destination, then the terminal action last. Still NOT ``role="menu"`` / ``includes/_overflow_menu.html``, and SNOW-921 makes that firmer rather than softer. An ARIA ``menu`` admits only menuitem / menuitemcheckbox / menuitemradio as children, so a ``role="switch"`` checkbox is not a valid child of one — and this surface now has a switch as its first control, plus a paragraph of prose above it. It is a disclosure holding a small form, which is what it has always actually been. Structure and dismissal come from the wrapper, not from here. The panel is included inside a ``

What it says — the content ``includes/_offline_banner.html`` carried before SNOW-748 deleted that strip: * the summary line — " — last synced ", where ``static/js/pwa_offline.js`` fills the ``data-role="synced-at"`` span with a relative phrase ("6 minutes ago") derived from ``sync.last_at``, the wall-clock time this device last reached the server, persisted to IndexedDB ``meta:app``. It falls back to an em dash until the first sync is known, and re-renders on a 30s timer while the panel is OPEN so the phrase counts up rather than freezing at the value it had when the user pressed the symbol. * the rubric — one explanation per state, all four rendered here and toggled by ``hidden``. * the way back to the network, as the one CTA at the foot. Four states, not three. The banner only ever appeared when something was wrong, so it had nothing to say about a working connection; the symbol this panel hangs off is permanent and pressable at any moment, so "everything is fine, and here is when you last synced" is now an answer a user can ask for. The other three are carried over unchanged: * online (``online-message`` / ``online-explainer``) — the app is using the network normally. * struggling (``offline-message`` / ``offline-explainer``) — requests are still being attempted, and the app will update as soon as one lands. * latched (``latched-message`` / ``latched-explainer``) — the service worker has stopped calling the network entirely after three consecutive read timeouts, and is serving downloaded data only. This state can be reached while ``navigator.onLine`` is still TRUE (a radio that is attached but has no route — the Underground), which is why nothing here keys off ``onLine`` alone. * forced (``latched-message`` / ``forced-explainer``) — the same behaviour, asked for by the user from the "Offline mode" switch BELOW. It shares the summary line, because the summary answers "is this app contacting the server" and the answer is the same; it does NOT share the explanation, because the latched one asserts there is no usable connection and here there may well be one. Nothing probes this state, so nothing will end it but the user. The online state is also what the panel renders BEFORE any script runs, which is the right default rather than a lucky one: both offline modes are service-worker decisions, and a page that got here without JavaScript has no worker and just came off the network. The CTA is still load-bearing, and SNOW-921 does not collapse it into the switch above it even though, in both offline modes, the two do the same thing. That redundancy is older than this surface: a signed-in user has had both controls since SNOW-748, in two different menus, and co-locating them reveals the duplication rather than creating it. Which of the two should survive is a product call, not a side effect of a move — see the ticket's "out of scope". One button, two labels: the action is identical but "Try reconnecting" reads as a repair, which is the wrong verb when nothing is broken and the user simply chose offline mode. ``pwa_offline.js`` hides the button in ``'auto'`` — where the app is already using the network — and while the app is merely struggling and still retrying on its own. Every user-facing string is rendered here and toggled by ``hidden`` rather than assigned from JavaScript: ``makemessages`` never scans ``static/js``, so a string set there ships as English to every locale, which is what ``bin/i18n-lint`` fails on (docs/i18n.md). Spec §3.5, §10.1, §12.6 — freshness is non-negotiable, and an app that has stopped asking the server has to say so. {% endcomment %}

Nothing about the mode ever needed an account: it is a row in this device's IndexedDB and a flag in this device's service worker. It is rendered for every viewer now. FIRST among the controls, directly under the rule. A real switch, on includes/_switch.html — the project's checkbox-with-role="switch" primitive — rather than a role="menuitemcheckbox" button. SNOW-921 drops the ``role="none"`` this row carried in the account menu. That attribute existed for one reason: a role="switch" checkbox is not a valid child of role="menu", and the account dropdown claims that role.
