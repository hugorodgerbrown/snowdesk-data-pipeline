{% load i18n components %} {% comment %} templates/includes/_connection_panel.html — the connection-status panel (SNOW-748), anchored to the header's connectivity symbol in ``includes/nav.html``. An ANCHORED POPOVER, not a toast. The first pass built this surface on ``includes/_toast.html`` and inherited three wrong answers from it: a toast is transient, system-initiated, bottom-centred and status-coloured, and this is none of those. It is user-invoked, persistent, and read at the point that opened it, so it hangs off that point and looks like the two dropdowns either side of it — the same ``absolute right-0 top-full mt-1.5 rounded-card border border-border bg-card shadow-md z-50`` chrome the account and admin menus use. Neutral card tokens, deliberately. The toast version passed ``kind="info"``, which painted the panel ``status-info`` blue while the header symbol beside it was painted ``status-warning`` amber for the same state — two surfaces disagreeing about one bit. The SYMBOL carries the status colour, because it is the thing that has to be legible without being opened; the panel is where the detail is read, so it is the card it sits on. It is not ``includes/_overflow_menu.html`` either: that partial is ``role="menu"``, which is a list of commands, and this is a paragraph of information with one button at the end of it. Structure and dismissal come from the wrapper, not from here. The panel is included inside a ``
`` in nav.html whose ```` IS the connectivity symbol, so open, close, Enter/Space and focus are the browser's, exactly as they are for the account and admin menus; nav.html's shared ``enhanceDisclosure`` script adds outside-click and Escape, and closes on the ``[data-disclosure-close]`` control below. Nothing here needs ``static/js/overlays.js``. The close control is that script's ``[data-disclosure-close]``, drawn with the ``icon_button_classes`` tag — the project's 44×44 icon-button idiom (``h-11 w-11``, the tap-target minimum), shared with every panel header's close. It sits top-right of the panel, pulled into the padding by its negative margins so the 44px box does not push the summary line down. Height-bounded and scrollable, because it floats over the map and that rule has no exceptions here: ``max-h-[60dvh] overflow-y-auto``, and ``dvh`` rather than ``vh`` because ``vh`` ignores mobile browser chrome and so resolves taller than the viewport exactly where the bound matters. The width is set for the same reason a floating box always needs one, and capped at ``calc(100dvw-2rem)`` so a narrow phone gets the panel rather than the screen edge. What it says — the content ``includes/_offline_banner.html`` carried before SNOW-748 deleted that strip: * the summary line — " — last synced ", where ``static/js/pwa_offline.js`` fills the ``data-role="synced-at"`` span with a relative phrase ("6 minutes ago") derived from ``sync.last_at``, the wall-clock time this device last reached the server, persisted to IndexedDB ``meta:app``. It falls back to an em dash until the first sync is known, and re-renders on a 30s timer while the panel is OPEN so the phrase counts up rather than freezing at the value it had when the user pressed the symbol. * the rubric — one explanation per state, all four rendered here and toggled by ``hidden``. * the way back to the network, as the one CTA at the foot. Four states, not three. The banner only ever appeared when something was wrong, so it had nothing to say about a working connection; the symbol this panel hangs off is permanent and pressable at any moment, so "everything is fine, and here is when you last synced" is now an answer a user can ask for. The other three are carried over unchanged: * online (``online-message`` / ``online-explainer``) — the app is using the network normally. * struggling (``offline-message`` / ``offline-explainer``) — requests are still being attempted, and the app will update as soon as one lands. * latched (``latched-message`` / ``latched-explainer``) — the service worker has stopped calling the network entirely after three consecutive read timeouts, and is serving downloaded data only. This state can be reached while ``navigator.onLine`` is still TRUE (a radio that is attached but has no route — the Underground), which is why nothing here keys off ``onLine`` alone. * forced (``latched-message`` / ``forced-explainer``) — the same behaviour, asked for by the user from the "Offline mode" switch in the account menu (``includes/nav.html``). It shares the summary line, because the summary answers "is this app contacting the server" and the answer is the same; it does NOT share the explanation, because the latched one asserts there is no usable connection and here there may well be one. Nothing probes this state, so nothing will end it but the user. The online state is also what the panel renders BEFORE any script runs, which is the right default rather than a lucky one: both offline modes are service-worker decisions, and a page that got here without JavaScript has no worker and just came off the network. The CTA is load-bearing. It asks for ``'auto'`` and it is the ONLY exit from an auto-latched state for a signed-out reader, who has no account menu and so no "Offline mode" switch. One button, two labels: the action is identical but "Try reconnecting" reads as a repair, which is the wrong verb when nothing is broken and the user simply chose offline mode. ``pwa_offline.js`` hides the button in ``'auto'`` — where the app is already using the network — and while the app is merely struggling and still retrying on its own. Every user-facing string is rendered here and toggled by ``hidden`` rather than assigned from JavaScript: ``makemessages`` never scans ``static/js``, so a string set there ships as English to every locale, which is what ``bin/i18n-lint`` fails on (docs/i18n.md). Spec §3.5, §10.1, §12.6 — freshness is non-negotiable, and an app that has stopped asking the server has to say so. {% endcomment %}
