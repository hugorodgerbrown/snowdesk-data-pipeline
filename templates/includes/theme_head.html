{% comment %} templates/includes/theme_head.html — Dark mode FOUC prevention. Include this in BEFORE the stylesheet link. It synchronously applies the .dark class to based on the user's saved preference (localStorage) or OS setting (prefers-color-scheme), preventing a flash of the wrong theme on page load. The `theme` key is written on the settings page, by includes/_theme_preference.html and static/js/theme_preference.js. It was not always: the setter shipped here as `window.__setTheme` for a toggle button that was never built, and SNOW-615 removed it as dead code — leaving this read with no matching write, so a value stored from a console call could never be changed or cleared by anything on the site. All three states below are reachable from that control. `dark` and `light` are pinned; "System" REMOVES the key, which is why the fall-through here is the system branch rather than a fourth case to add. A stored value that is neither `dark` nor `light` also falls through, so junk in the key is harmless rather than sticky. The `dark` class this puts on is the resolved answer, and theme_preference.js re-applies it directly rather than reloading the page. The boolean below is mirrored there — it cannot be shared, because this script has to be inline and parser-blocking to beat the stylesheet, so it can neither import nor be imported. Two copies, one rule: keep them in step (the reasoning is written out in theme_preference.js's header). The localStorage read is wrapped: Safari in private browsing, and any browser with site data blocked, throw on access rather than returning null. Unwrapped, that exception would abort this script before the class is applied — turning a storage restriction into a permanently light-themed page for a user whose OS is dark. {% endcomment %}
