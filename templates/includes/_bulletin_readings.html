{% load i18n components %} {% comment %} includes/_bulletin_readings.html — where this day's line meets this day's bulletin (SNOW-839, shared by SNOW-973). The one thing on a trip page that changes twice a day. Everything else is the snapshot the organiser shared; this is read fresh on every view and stored nowhere on the SERVER, because a cached intersection would be held under a date it no longer belongs to. TWO SURFACES SINCE SNOW-973. It began as trips/partials/_trip_bulletin.html and never dereferenced ``trip`` — only ``bulletin_readings`` — so the move here was a rename plus the two parameters below. The map's route detail panel renders the same rows for a saved route on the day the scrubber is showing; a route's reading is fetched per open rather than rendered into a page, and what the CLIENT then holds of it is bounded by static/js/routes_bulletin_offline.js, which stamps every cached row with the freshness envelope the response carried and renders an expired one as expired rather than as a current reading. WHAT THIS IS NOT. It is not a score, not a verdict and not a recommendation, and the copy is written so it cannot be read as one. A number would suppress everything it did not weigh, invisibly — and ``docs/decisions/location-first-information-model.md`` already draws that line: highlight, never suppress, which is "the line between helping someone read a bulletin and deciding for them, and it is what our liability disclaimer rests on". So every row states a fact about the TRACK ("1.4 km of your line, on N and NE, between 2200 and 2800 m") and names the problem the forecaster put there. The deciding is the reader's, with the bulletin this panel links them to. ONE BLOCK PER REGION, longest stretch first. A track over a ridge is in two micro-regions, and on a border it is two PROVIDERS with two readings of the same day — so the panel shows both rather than picking one, and names each. A region with no bulletin for the day is still listed: a reader whose route leaves the forecast needs to know it did. Context: bulletin_readings: list[dict] — one entry per region, each carrying ``region``, ``bulletin``, ``bulletin_url``, ``overlaps`` (already display-shaped) and ``length_km``, the region total. Built by ``apps.routes.services.route_bulletin.display_readings``. Optional context: testid_prefix : str — prefix for the two test hooks below; defaults to ``trip-bulletin``, which is what the trip page's own tests have always looked for. The route panel passes ``route-bulletin`` so a test can say WHICH surface it found the rows on. card_extra : str — extra utilities for the card chrome. The trip page passes ``mt-3``, the gap every other card there carries — the notes, the details, the map. Without it this card butted straight onto the map card's footer and the two read as one surface.
