THE ROUTES ROW'S ORDER, AFTER ONE ITEM OF ITS OWN. Terrain and bulletin → rule → Plan a trip → Share → rule → Rename → Delete. The last four are exactly routes/partials/_route_row_menu_items.html's: design-system rule 4 puts an action where the user already learned it is, and the rail offers the same four things for the same route. The first is the rail's alone — it opens the route detail sheet, which a tap no longer opens — and it reads the route rather than acting on it, so it leads and a rule sets it apart. Destructive stays last. A PENDING SHARE KEEPS ONLY THE FIRST. Its reading needs no ownership; the other four are owner-only endpoints addressed by a uuid a recipient is never handed. static/js/route_rail.js hides each owner-only item (`data-route-rail-owner`) individually rather than the whole menu. WHAT DIFFERS FROM THE ROW, AND WHY. The row is rendered server-side for one known route, so its items carry that route's uuid and its Delete is an HTMX form. The rail is rendered ONCE, empty, and filled by static/js/route_rail.js for whichever route is open — so every item here carries a bare hook the script writes the uuid onto, and Delete is a button the script confirms and posts. No `hx-*` attribute is rendered here, which is what keeps home.html's htmx pairing (tests/public/test_htmx_is_loaded.py) unchanged. Rename keeps the row's two hooks: `data-row-rename`, which static/js/inline_rename.js recognises as a rename click, and `data-route-rename`, which carries the uuid for static/js/row_rename_commit.js. The rail's identity block is the `[data-row-renameable]` they resolve against. The visible label is the accessible name throughout: the row's items name their route in an aria-label because a list holds many, and the rail holds one, named in the heading beside the trigger. {% endcomment %}
