THE ROUTES ROW'S ORDER, MINUS NOTHING. Plan a trip → Share → rule → Rename → Delete, exactly as routes/partials/_route_row_menu_items.html has it: design-system rule 4 puts an action where the user already learned it is, and the rail offers the same four things for the same route. Destructive stays last. WHAT DIFFERS FROM THE ROW, AND WHY. The row is rendered server-side for one known route, so its items carry that route's uuid and its Delete is an HTMX form. The rail is rendered ONCE, empty, and filled by static/js/route_rail.js for whichever route is open — so every item here carries a bare hook the script writes the uuid onto, and Delete is a button the script confirms and posts. No `hx-*` attribute is rendered here, which is what keeps home.html's htmx pairing (tests/public/test_htmx_is_loaded.py) unchanged. Rename keeps the row's two hooks: `data-row-rename`, which static/js/inline_rename.js recognises as a rename click, and `data-route-rename`, which carries the uuid for static/js/row_rename_commit.js. The rail's identity block is the `[data-row-renameable]` they resolve against. The visible label is the accessible name throughout: the row's items name their route in an aria-label because a list holds many, and the rail holds one, named in the heading beside the trigger. {% endcomment %}
