Revealed by static/js/pwa_offline.js when: * ``navigator.onLine === false``, or * a fetch / HTMX request just failed with a network error, or * the service worker has latched into offline mode (SNOW-742 — see below; this one can be true while ``navigator.onLine`` is still true). The summary row reads "Offline — last synced ", where ``static/js/pwa_offline.js`` fills the ``data-role="synced-at"`` span with a relative phrase ("6 minutes ago") derived from ``sync.last_at`` — the wall-clock time this device last reached the server, persisted to IndexedDB ``meta:app``. The phrase re-renders on a timer while the banner is shown, so an open banner keeps counting up rather than freezing. It falls back to an em dash until the first sync is known. Opening the caret reveals a short explanation of the offline state. There is one clock, not two: a ``freshness.last_generated_at`` companion read from ``X-Data-Generated-At`` (SNOW-370) was absorbed and persisted but never surfaced anywhere, and SNOW-615 removed it. SNOW-742 — two states, not one. The banner now distinguishes "the network is failing" from "the app has given up on the network", because they make different promises to the user and only one of them is true at a time: * struggling (``offline-message`` / ``offline-explainer``) — requests are still being attempted, and the app will update as soon as one lands. * latched (``latched-message`` / ``latched-explainer``) — the service worker has stopped calling the network entirely after three consecutive read timeouts, and is serving downloaded data only. This state can be reached while ``navigator.onLine`` is still TRUE (a radio that is attached but has no route — the Underground), which is exactly why the banner cannot key off ``onLine`` alone. * forced (``latched-message`` / ``forced-explainer``) — SNOW-748: the same behaviour, asked for by the user from the header toggle (``includes/nav.html``). It shares the summary line, because the summary answers "is this app contacting the server" and the answer is the same; it does NOT share the explanation, because the latched one asserts there is no usable connection and here there may well be one. Nothing probes this state, so nothing will end it but the user. Both variants of the message and the explanation are rendered here and toggled by ``hidden`` in static/js/pwa_offline.js, rather than having their text set from JavaScript: ``makemessages`` never scans ``static/js``, so a string built there ships as English to every locale. ``bin/i18n-lint`` enforces this. See docs/i18n.md. One button, offered only where it does something: the way back to normal operation, shown under either offline mode and hidden while the app is merely struggling. Its label switches with the mode ("Try reconnecting" when the app gave up, "Use the network again" when the user did). SNOW-748 removed the "Stay offline" button that used to sit beside it. It was the control for a user who has signal and is about to lose it, and it lived inside a banner that only appears once the signal has already gone — unreachable for its own case. It is now the always-visible network toggle in includes/nav.html. Spec §3.5, §10.1, §12.6 — freshness is non-negotiable, and an app that has stopped asking the server has to say so. In-flow, not ``fixed`` — it sits as the first child of the body, above ``includes/nav.html``, so when revealed it pushes the nav and page content down rather than overlapping the nav bar. ``hidden`` collapses it to zero height.
