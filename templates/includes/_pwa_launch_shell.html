{% load i18n static %} {% comment %} templates/includes/_pwa_launch_shell.html — PWA launch shell (SNOW-878). The second half of the splash. The iOS startup images (includes/_pwa_splash.html) cover from tap to first paint; this covers from first paint to the app being worth looking at — on the map page that is the gap while MapLibre fetches its style and first tiles, during which the page has painted chrome over an empty #map. It is drawn to MATCH the OS launch screen exactly: same background token, same tile, centred, same proportion of the shorter edge (the clamp in .pwa-launch-shell__mark mirrors iconPixelsFor() in bin/build-pwa-splash). Done right the user never sees a handover at all — one splash that happens to change owner halfway through. WHO SEES IT Only a cold launch of the INSTALLED app. Two gates, both in the inline script below: * standalone — display-mode: standalone, or iOS Safari's legacy navigator.standalone. A browser tab is not launching an app; a splash there is an interstitial nobody asked for. * once per launch — a sessionStorage flag. In a standalone window that storage lives exactly as long as the app does, so "not yet set" means "this is the launch". Without it, every in-app navigation back to a full page load would replay the splash. WHY THE GATE IS AN INLINE SCRIPT It has to resolve BEFORE first paint, or the overlay flashes on the two populations that must never see it. A deferred external script runs after paint, and CSS alone can express display-mode but not the session flag. This is the same constraint, and the same solution, as includes/theme_head.html — which is also why the failure mode is "overlay never shows" rather than "overlay never leaves": the class is only ever added, never relied on for removal. Removal is the deferred script's job (static/js/pwa_launch_shell.js), backstopped by a CSS failsafe animation in src/css/main.css so a script that never parses cannot leave the app covered. {% endcomment %}
