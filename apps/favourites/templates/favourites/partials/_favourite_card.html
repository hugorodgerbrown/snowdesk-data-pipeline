Content: 1. Title, altitude, and a link that finds the pin on the map. The title is the pin's name, falling back to "Unnamed pin" — the same words the row above it uses, so one pin does not have two names. It fell back to the pin's own coordinates until SNOW-711, which made a nameless pin's heading a pair of five-decimal numbers: precise, unmemorable, impossible to place, and the least useful thing the card could have led with. The coordinates keep their place on the card, one line lower and doing a job instead: they are the visible text of a link to /map/?favourite=, which flies the map to that pin and opens its popup (map.js's own deep link, SNOW-711). Reading a coordinate tells nobody where a place is; going there does. The crosshair (includes/_icon_locate.html) marks it as an action rather than a stray figure — see that file for why it is not the favourites star. 2. Avalanche danger — regional. The containing MicroRegion's name and today's danger-tile chip (when a RegionDayRating exists), linking to the evergreen bulletin page. When favourite.region is None (the pin falls outside every known boundary), a "no bulletin coverage" note is shown instead. Copy states plainly the rating is for the whole region, not this exact spot. 3. Weather — this spot. Renders forecast_panel (a compact multi-day strip plus expandable hourly detail, from build_point_forecast_panel over the point's own ForecastCellWeather window, SNOW-417) when present; otherwise an explicit "coming soon" empty state. Deliberately never falls back to the region's WeatherSnapshot. 4. Avalanche problems — this location (SNOW-422). Only rendered when problem_cards is non-empty (region + today's default bulletin both resolved). One _favourite_problem.html per card, each carrying an altitude annotation relative to favourite.elevation — every problem the bulletin publishes is always shown; the annotation only highlights relevance, it never suppresses a card. THE CARD SHOWS A FAVOURITE; IT DOES NOT MANAGE ONE. It carried a fifth section until SNOW-711 — "Rename / delete controls", a copy of the list's own row (_favourite.html). That made sense while the card appeared in #favourite-card-panel at the TOP of the account page, detached from the row that opened it: the card was the only place its own pin's controls were within reach. SNOW-711 moved the card UNDER its row, and the section became a second copy of that row sitting fourteen pixels below the first — same label, same meta line, same pencil and trash. Hugo, seeing it: "There is a rogue repeat of the row?" It was, and giving the copy its own id (which this file did for one commit) fixed the id collision while leaving the duplication on screen. So managing a favourite belongs to the surface that LISTS it — the account row and the map row, both of which are one row per pin. The same split the map already had: its row manages, its card reads. On the standalone favourite_detail.html the controls are not replaced by anything, and are not missed: that page has never loaded htmx, so the rename form and Remove button it inherited here were inert from the day SNOW-507 shipped them.
