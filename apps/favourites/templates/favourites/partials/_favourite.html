{% load i18n %} {% comment %} favourites/partials/_favourite.html — one saved-pin row. The ONE saved-pin row: every surface that lists a favourite renders this file (SNOW-711). Rendered directly by apps.favourites.views.favourite_create, favourite_resort_create and favourite_rename after a write, and looped over by both list variants (_favourite_list.html on /account/, _favourite_list_map.html in the map sheet). WHAT THIS REPLACED. Until SNOW-711 this row was a bordered box holding an always-visible text input and an underlined "Remove", and the map sheet had a SECOND row (_favourite_row_map.html) built from the shared UGC row — because SNOW-658 gave the map panels one row anatomy and the account page never adopted it. So the same pin read one way on the map and another on /account/, and the account page was the last surface in the codebase managing user data with a text field and a text button. Both files are this one now, and the map row's own rationale is kept below. * a row is not a card. It draws a hairline and nothing else (includes/_ugc_panel_row.html), so a list reads as a list; * rename is the pencil, and happens IN PLACE on the label. The always-visible input it replaces was not reachable without JS anyway — the hub loads this list by hx-get, so a no-JS visitor gets "Loading…" and nothing else — and a list of live inputs is not a list at rest; * Remove is the trash, last in the row, in the same place on every list a user meets. Meta line: when the pin was saved, prefixed with its region when one matched — "Alpstein · saved 3 Feb 2026", Hugo's own design for this row. It used to be the region, falling back to the pin's coordinates. Two problems with that. The coordinates are the wrong reading: a pair of four-decimal numbers is precise, unmemorable and impossible to place, so the line said least exactly where it was the only thing on offer (an unnamed pin outside every known boundary). And the date was missing altogether, though it is the one fact that orders a list of saved places and tells a user which of two similar pins is the recent one. Region is nullable — a pin can fall outside every known boundary — so the date alone is the default and the joined form exists only for the case that has both. Same shape, and the same date format, as the observation row (observations/partials/_observation.html), which had the pairing right first. No `value` slot: that column is for measured quantities (downloads' size) and a favourite has none. Leaving it out is the point — a column that means "size" on one panel and something else on another means nothing. THE DISCLOSURE IS ON BY DEFAULT, and one caller turns it off. That is the right way round because of who this row is answered TO: favourite_rename returns it to the account page, which swaps it straight back into the row it came from, and a row that lost its chevron on rename would be a row that quietly stopped expanding. The map sheet is the exception (SNOW-658, Hugo's design: a pin's detail is reached by tapping the pin, which is where that user already is). Context: favourite : Favourite — the saved pin to render. hide_disclosure : bool, optional — drop the trailing chevron.
