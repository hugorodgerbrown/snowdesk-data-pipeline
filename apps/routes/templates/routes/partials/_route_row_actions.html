TWO CLUSTERS, AND WHICH ONE RENDERS IS DECIDED BY OWNERSHIP (SNOW-764). An OWNED row gets ONE "…" trigger (SNOW-830) opening a menu that holds Plan a trip, Share, Rename and Remove — Share only when ``sharing_enabled`` says so, which is a surface check and nothing else: which listing asked, and therefore whether a handler is wired for the click (see apps/routes/views.py's route_list). The items themselves, their order and every hook on them live in _route_row_menu_items.html. WHY A MENU HERE AND NOWHERE ELSE. SNOW-764 put a Share icon on this row and SNOW-819 added a full-width "Plan a trip" text link, which made four controls competing for the right-hand end of a 380px panel row; the route's name — the one thing a user scans the list by — rendered as "Mont Fort – Ba…". SNOW-658's "no ellipsis menu on any panel" ruling is narrowed to exclude this row rather than withdrawn: favourites, field observations and downloads all still have room for a visible trash, and keep it, because one tap beats two wherever the row can afford it. A PENDING row — one the visitor was sent and has not claimed — gets a single Save. It is not an icon: the other three name actions a user already understands from every other panel, while this one is the whole point of the row and the only thing on the surface asking to be pressed. A 17px glyph for the row's primary action would be a puzzle. The pending branch is itself two states, on authentication. A signed-in visitor gets the Save form; an anonymous one gets a link to sign in, because routes:share_claim answers a claim with no account to claim onto with a 403 — and the same control is what the map popup draws for the same visitor (static/js/map.js's appendRouteClaimCta). Never nothing: the reason they are on this surface at all is that somebody sent them the route. The two never both render. A pending row's route is not the viewer's, so Rename and Remove have nothing to address — and they are owner-scoped server-side anyway, so a rendered pencil would be a control that 404s. WHY THE PENDING BRANCH CARRIES A TOKEN AND NEVER A UUID. The rename and delete endpoints are addressed by ``route.uuid`` and owner-scoped, so a uuid rendered for a non-owner would hand them an identifier they have no business holding — see apps/routes/views.py's header. ``pending_share`` is what _route.html passes instead, and the claim endpoint is addressed by its token. WHAT THE MENU'S IDS ARE, AND WHY THEY ARE PER-ROW. A panel lists many routes and each renders this partial, so `trigger_id`/`menu_id` are keyed on the route's own uuid — the trigger's `aria-controls` has to name one element. static/js/overflow_menu.js itself never reads them (it is scoped by `closest()`, not `getElementById`); they exist for ARIA correctness. The trigger's own aria-label names the row for the same reason the items' do: "More actions" alone names nothing with a list of rows on screen. ``row_target`` rather than a hardcoded ``#route-``: the shared row takes its own DOM id as a parameter, and a Remove that named the id directly would go on addressing the default one whatever the row was given. Same contract as the favourite row's actions. It is passed through to the menu items, which own the Remove form. WHAT THE MENU DID NOT CHANGE. Every hook the four controls carry is the one it already was, and none of the five modules that read them noticed the move — each resolves by upward `closest()` traversal or a row-scoped `querySelector`, never by depth or sibling position, and every listener is delegated on the sheet or on document.
