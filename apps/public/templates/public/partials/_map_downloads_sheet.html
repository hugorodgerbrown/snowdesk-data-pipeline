{% load i18n static components %} {% comment %} public/partials/_map_downloads_sheet.html — "Manage downloads" sheet (SNOW-588; the way in rewritten by SNOW-634; SNOW-635 lets more than one custom area be listed, and adds Rename). The surface that answers "what have I stored offline, and what is it costing me". Opened from ``#map-custom-download-control`` (the bottom-right roundel — public/partials/_map_custom_download_control.html) and driven by static/js/map_downloads_manager.js. SNOW-588 through SNOW-632 reached this sheet only via a ``[data-menu-action="manage-downloads"]`` row buried in the layers menu, while the roundel opened a DIFFERENT surface (the "Download a custom area" framing overlay) directly. SNOW-634 collapses the two: the roundel now opens THIS sheet, the menu row is gone, and "Download a custom area" became an action INSIDE the sheet instead — the ``[data-downloads-add]`` trigger, handled by map_downloads_manager.js's delegated click listener (offline: disabled and relabelled — SNOW-637; online: hide this sheet and call ``window.pwaCustomAreaDownload.openFraming()``, map.js's own bridge for it). SNOW-641 settled the running order, which had accreted rather than been chosen: the list first, then the add-trigger under it, then the budget control with the running total and its bar grouped into one bordered block at the foot. Previously the total led the sheet and the trigger sat above the list, so the two things a reader wants — what is stored, and how much room is left — were at opposite ends with the list between them. Nothing here is positional as far as the JS is concerned: every element is addressed by data-attribute, never by index or sibling relationship, so this order is a presentation decision and can be revisited as one. It lives on the map, rather than under account settings, for two reasons. Downloading happens here, so managing downloads belongs here; and the list has to name each area, which on the map is free — ``FEATURE_BY_REGION_ID`` already holds every region's name from the SW-cached ``regions.geojson``, so the names resolve offline, which is exactly when storage pressure is felt. An account page would also imply the list follows the user between devices, and it emphatically does not: Cache Storage is per-browser, so both the downloads and the budget are **device-local**.
