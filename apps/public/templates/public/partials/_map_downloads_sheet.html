SNOW-634 collapses the two: the roundel now opens THIS sheet, the menu row is gone, and "Download a custom area" became an action INSIDE the sheet instead — the ``[data-panel-add]`` trigger, handled by map_downloads_manager.js's delegated click listener (offline: disabled and relabelled — SNOW-637; online: hide this sheet and call ``window.pwaCustomAreaDownload.openFraming()``, map.js's own bridge for it). SNOW-645 review supersedes SNOW-641's running order (list, then trigger, then a bordered budget block at the foot): the budget moved back to the TOP, folded into the header block itself, because Hugo's design reads it as part of "what this sheet is" rather than a footnote below the list — the opposite conclusion SNOW-641 drew, and worth noting so a future reader does not assume SNOW-641's reasoning still holds. A second SNOW-645 review pass moved the overlay switch ("Show areas on the map" then, "Display on the map" since SNOW-658) from between the budget caption and the REGIONS heading down to the very foot, below the add-custom-area CTA — Hugo's own instruction, so the map BEHIND the sheet is the last thing read, not the first. Nothing here is positional as far as the JS is concerned: every element is addressed by data-attribute, never by index or sibling relationship, so reordering never needs a JS change. It lives on the map, rather than under account settings, for two reasons. Downloading happens here, so managing downloads belongs here; and the list has to name each area, which on the map is free — ``FEATURE_BY_REGION_ID`` already holds every region's name from the SW-cached ``regions.geojson``, so the names resolve offline, which is exactly when storage pressure is felt. SNOW-749 changed what this list means, and the paragraph that used to stand here said the opposite. It read: an account page "would also imply the list follows the user between devices, and it emphatically does not". It does now. The DEFINITION of each area — which region, or which framed box, under which basemap, called what — is a row on the user's account (apps/downloads/), so an area saved on a laptop is listed on a phone with a one-tap "Download here". What did NOT change is the part that made the old claim worth making. Cache Storage is per-browser, so the BYTES and the BUDGET are still device-local, and a row can be on this list and not be available offline here. Every string below is written to hold that line: an account-only row is dimmed, carries no size, says "not downloaded here", and never paints anything that reads as cached. The panel still lives on the map for the two reasons above — where the download happens, and where the names resolve offline.
