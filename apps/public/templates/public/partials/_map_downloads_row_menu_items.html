THE RULE THIS IMPLEMENTS, which supersedes the one the shared row partial and the overflow-menu partial both still described: **more than one action on a row is a "…"; exactly one action is a bare icon.** SNOW-658 ruled the other way (a visible trash on every row, one tap not two) and SNOW-830 narrowed it for the routes row alone; Hugo reversed it on 2026-09-07 for every panel. On this panel it means: a REGION on this device Remove alone → the bare trash stays. a CUSTOM AREA or DROP ZONE Rename and Remove → this menu. a row NOT on this device Download alone → the bare download icon. a row that cannot render Repair and Remove → this menu. a row whose CONTENT is short Refresh content and Remove → this menu. SNOW-932 added the last of those. It is a different fault from Repair and it is deliberately its own item: Repair fetches the documents the map needs to DRAW, and this fetches the bulletins and weather inside the boundary, which is what the map draws them ON. A custom area or drop zone had neither signal nor remedy for the second before that ticket — the only way to re-fetch a few kilobytes of bulletins was to delete the area and re-spend megabytes of tiles. Order follows the design-system consistency rule: the constructive items first in the order the routes and favourites rows established, destructive last.
