{% load i18n components %} {% comment %} public/partials/edit_locations_panel.html — edit-locations mode side panel. Rendered from public/home.html when the request hits /?edit=locations AND the request user is a superuser. The gate is the view's (``_edit_target``) and the API's (``_require_edit_map_admin``); the panel is only the UI affordance. Hydrated by static/js/map_edit_locations.js, whose logic lives in static/js/map_edit_locations_core.js. The catalogue, the resort list and both vocabularies (Location.KIND, ResortLocation.ROLE) arrive in one fetch of ``api:edit_locations_queue``. THREE MUTUALLY-EXCLUSIVE MODES, one panel: create — "New location": name it, classify it, drop a pin, and name the first resort it belongs to. A location with no resort is invisible to every surface that reads one, so the first link is part of creating it rather than a second step. edit — a catalogue row is selected: move the pin, rename, re-kind. The edit reaches EVERY resort linked to it, because they share one row — which is the point. link — the same selected row, attached to ANOTHER resort. The mode the resort editor has no equivalent of, and the reason the estate exists: Mont Fort is one row that Verbier, Nendaz, Veysonnaz and Thyon reference, not four pins on one summit. Exclusivity is enforced in ``map_edit_locations_core.js``'s ``reduceMode`` / ``visibleSections``, not by three independent booleans here — two forms on screen would mean two Save buttons writing to two endpoints. kind vs role: ``Location.kind`` describes the place, and lives in the create/edit block. ``ResortLocation.role`` describes one resort's relationship to it, and lives in the create and link blocks. They are never derived from one another — a point can be one resort's top and another's mid-station. An edit lives only in this environment's database until ``manage.py dump_locations_sheets --commit`` writes it back to apps/locations/data/, which the header says out loud. {% endcomment %}
