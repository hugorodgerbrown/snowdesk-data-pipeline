{% load i18n %} {% comment %} public/partials/edit_resorts_panel.html — edit-resorts mode side panel. Rendered conditionally from public/home.html when the request hits /?edit=resorts AND settings.DEBUG is True. The DEBUG guard lives at the API endpoints; the panel just provides the UI affordance. Hydrated by static/js/map_edit_resorts.js — the catalogue is fetched once and rendered as a flat alphabetical list with Set/Unset/Review pills (SNOW-85 manual workflow; replaces the SNOW-74 grouped queue of unset resorts). The search input filters the same list in place. Several DOM IDs (edit-resorts-queue, edit-resorts-remaining) keep their SNOW-74 names for minimal-diff reasons even though they no longer correspond to a queue concept — the JS comments explain. "New resort" (``edit-resorts-new``) switches the same target block into create mode: the Name/Canton inputs appear, the pin is placed exactly as for an edit, and Save posts to ``api:edit_resort_create`` instead — which derives the parent region from the pin, so there is no region picker here by design. Name is the only required input; a blank canton is inherited from the derived region's existing resorts server-side (``apps.public.api._canton_for_region``), and the input is there to override that for a border case. The "Resort details" section edits the hand-curated metadata fields added by SNOW-500 (lifts, runs, piste length, elevations, season dates, operator, website) plus the SNOW-542 ``why_it_matters`` line. Every input carries ``data-resort-field=""``; the JS reads and writes the whole set generically off that attribute, so adding a field here needs no JS change — only a matching entry in ``apps.regions.forms.RESORT_DETAIL_FIELDS``, which is what the API validates and persists. {% endcomment %}
