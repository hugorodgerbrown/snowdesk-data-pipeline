THE PAGE THE MAP CARD HANDS OFF TO. Tapping a weather symbol opens a card carrying today's conditions and a "View forecast" link; this is what that link opens, and it holds everything the card deliberately drops — the week, and the hourly detail at full resolution. The card is a glance; this is the read. It is keyed on ``Location`` rather than on a resort or a region because most of the estate is neither. 461 of the 540 public locations are ``MicroRegion`` centroids: before this page they had no destination at all, so the card's link would have been missing on the large majority of taps. **Built around one question: which day are you planning for** (SNOW-789). Five hairline-separated regions, top to bottom: 1. Masthead includes/_weather_masthead.html — name, elevation, onward links. 2. Day picker includes/_weather_day_picker.html — the week as NAVIGATION: seven cells carrying weekday, icon and high/low, nothing else. 3. Selected day includes/_weather_day_line.html — date, condition, freezing level, daylight. 4. Meteogram includes/_hourly_chart.html — that day's hours, when the day has an hourly series. 5. Provenance includes/_weather_provenance.html — updated, source. Everything below region 2 describes the ONE day the picker has selected. The layout this replaces stated the same high and low three times — in a "Today" panel, in the day cells, and as the shape of an outlook chart — and named the location again in every sub-header. ``includes/_weather_panel.html`` and ``includes/_forecast_chart.html`` are gone from this page for that reason; the panel keeps its other three consumers, the chart was deleted. Three page shapes, discriminated by ``show_day_picker`` and NEVER by the date: live row 7 cells; days 1–2 reveal a day line AND a meteogram, days 3–7 reveal a day line alone. backfilled row ``forecast=None`` is one day, so no picker: the day line and its meteogram render plainly, with no hiding class — with no radio the ``:has()`` reveal could never match. no row at all the "nothing recorded" message. The reveal is CSS-only — see the "Forecast day selector" block in src/css/main.css and the note there about why the rules are written by hand rather than with Tailwind's ``peer-checked:``. Context: location — locations.Location. heading — str, resolved by the view. resort — regions.Resort the location belongs to, or None. region — regions.MicroRegion the location is the centroid of, or None. observed_on — datetime.date being shown. weather — weather.Weather row, or None. panel — ForecastPanel, or None. show_day_picker — bool, precomputed by the view: the row carries more than one day. hourly_charts — list of {"index", "chart"}, one per day with a series. ``index`` is the day's position in panel.days, which is what ties a meteogram to the cell that selects it. {% endcomment %} {% block page_meta %} {% blocktrans with name=heading trimmed asvar page_title %}{{ name }} weather · Snowdesk{% endblocktrans %} {% blocktrans with name=heading trimmed asvar page_description %} Mountain weather forecast for {{ name }} — conditions, temperature outlook and hourly detail. {% endblocktrans %} {% include "includes/_page_meta.html" with title=page_title description=page_description %} {% endblock page_meta %} {% block content %}

The script was loaded by /_components/ alone, so the button rendered on this page — the only page that ships the chart — with nothing listening: it carried ``aria-expanded="false"`` for its whole life and never changed it. Not in base.html, because this is the only page that renders a chart. The handler delegates from the document and scopes each open to the chart's own ``role="group"`` root, so the two meteograms a live row produces get one legend each rather than fighting over the first. Everything else on this page — the day picker, the day-line reveal — is CSS only and needs no script. The legend degrades the way its own module says it should: the chart stays readable, and the key explaining its marks is what is lost. {% endcomment %} {% endblock extra_js %}
