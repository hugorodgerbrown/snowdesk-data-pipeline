{% extends "public/base.html" %} {% comment %} apps/public/templates/public/resort.html — Public resort detail page (SNOW-504). Gives a Resort its own indexable URL (``/resorts//``), rendered by ``apps.public.views.resort_detail``. Cross-linked from the map's resort-pin popup, whose CTA reads "View resort →". THE PAGE ANSWERS THE QUERY (SNOW-1124, docs/decisions/a-resort-page- answers-the-query.md, amending SNOW-807's docs/decisions/two-documents-and- a-map.md for resort pages). People search "Verbier avalanche", not "CH-4115", and a page that only links onward cannot rank for that — so today's danger is shown here. It is the bulletin page's own render model, selected the same way and rendered through the same partials, read-only: the bulletin stays the one full document, and this page holds no copy. Sections, top to bottom: 1. Resort name (+ alternative/marketing name, when set), canton, and parent region name, then the curated "why it matters" line (SNOW-542) via the shared ``public/partials/_resort_why_it_matters.html`` partial, which owns its own blank state, then the curated facts block (SNOW-695) via ``public/partials/_resort_facts.html`` — operator, website, lifts, runs, piste, elevation range, season and notes, each cell omitted when unset and the whole block omitted when all are. The resort's own. 2. Today's danger (SNOW-1124). ``[data-testid="resort-danger"]`` is ONE link to the parent region's evergreen bulletin, carrying today's ``.danger-tile`` and level word (or the no-bulletin note) and the "Full bulletin →" label, followed by the bulletin headline (``public/_bulletin_headline.html``). tests/e2e/test_resort_page.py clicks ``[data-testid="resort-danger"] a`` — keep exactly one. Below it, OUTSIDE that block because their prose and field notes can carry links, the avalanche problem cards (``public/_rating_block.html``, the bulletin page's own loop) with aspects, elevations and the full problem prose. With no bulletin covering today only the note and the link render — never a past bulletin as today's. 3. The favourite/unfavourite control (``favourites/partials/_resort_favourite_button.html``). 4. Forecasts — a plain list of the resort's curated locations, each a link to its own weather page (``/weather//``), with the role and elevation that tell village from summit. No weather data is read here: SNOW-761 drew one block per location and SNOW-783 trimmed it to the day; this removes the rest. A resort with no curated locations renders no section at all — ``link_resort_locations`` is a manual operator step, so that state is normal. 5. Observations — ONE link to the map with the reports sheet open, flown to this resort (``?panel=reports&resort=``). The point-local counts SNOW-508 rendered here were a filtered view of map data. Resorts with ``needs_review=True`` or null coordinates still render here — only the map-anchor affordance is skipped, and this page has none.
