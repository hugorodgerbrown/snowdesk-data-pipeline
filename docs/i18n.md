# Internationalisation

Settings (`config/settings/base.py`):
- `LANGUAGE_CODE = "en-gb"` — British English, matching the project spelling convention.
- `LANGUAGES = [("en", "English")]` — single-language catalogue for now.
- `LOCALE_PATHS = [BASE_DIR / "locale"]` — `.po` / `.mo` files live under `locale/en/LC_MESSAGES/`.

**Template strings**: use `{% load i18n %}` at the top of every template that wraps strings.
- `{% trans "string" %}` for short single-line strings without variables.
- `{% blocktrans with var=value %}...{{ var }}...{% endblocktrans %}` for strings with
  template variables.
- `{% blocktrans trimmed %}` when spanning multiple lines.

**Python strings**:
- `from django.utils.translation import gettext_lazy as _` at module scope for import-time
  strings (dict values, `TextChoices` labels, render model labels).
- `from django.utils.translation import gettext as _` inside functions for request-time
  strings (view helpers, template tag filters).
- Always use `%`-formatting with named placeholders for translatable strings that
  contain variables: `_("above %(bound)s") % {"bound": lower_fmt}`. Never f-strings —
  `xgettext` cannot extract them.

**Do NOT wrap**:
- SLF bulletin prose (`|snowdesk_html` / `|safe` content arriving from the API).
- Logging messages — these are operator-facing, not user-facing.
- `_TITLE_FALLBACK` values in `render_model.py` — persisted to the DB JSON field as plain strings.
- `apps/bulletins/templates/admin/*` — staff-only admin/ops UI, English-only by design.

## JavaScript strings

`makemessages` scans templates and Python. It **does not scan JavaScript**, so a
string written as a JS literal never reaches the catalogue and ships as English
to every locale. SNOW-620 marshalled the ~45 that had accumulated.

The pattern: the surface's own partial renders a hidden `<template>` of
`{% trans %}` spans, and the module reads it back through
[`static/js/i18n_strings.js`](../static/js/i18n_strings.js).

```html
{# in the surface partial #}
<template id="report-strings-template">
    <span data-string="generic">{% trans "Something went wrong — please try again." %}</span>
    <span data-string="usage">{% blocktrans %}%(used)s of %(budget)s used{% endblocktrans %}</span>
</template>
```

```js
// in the module — the literals are the English FALLBACK, not the source of truth
const STRINGS = self.pwaStrings.read('report-strings-template', {
  generic: 'Something went wrong — please try again.',
  usage: '%(used)s of %(budget)s used',
});
el.textContent = STRINGS.generic;
el.textContent = self.pwaStrings.interpolate(STRINGS.usage, { used, budget });
```

Rules:

- **Always keep the English fallback.** A page that omits the partial must still
  render words, not `undefined`.
- **Substitute placeholders by name** (`%(date)s`), never by concatenation — a
  locale is free to reorder them, or to need different words on either side.
- **`escapeHtml()` when the surface assembles `innerHTML`.** Ordinary punctuation
  in a translation would otherwise close an attribute early. Prefer `textContent`,
  which needs no escaping.
- **`|escapejs`, not the default autoescaping**, when a `{% trans %}` value is
  interpolated into a JS string literal in a template. HTML-escaping renders an
  apostrophe as `&#x27;` on screen, and a double quote breaks the literal outright.
  Use the `{% trans "…" as var %}` + `{{ var|escapejs }}` form — `{% trans %}`
  takes no filter.
- **Load `i18n_strings.js` before any consumer.** Every script is `defer`, so
  document order is execution order; `public/base.html` loads it near the top of
  the script block, and `admin/base_site.html` loads its own copy.

Enforced by **`tox -e i18n-lint`** ([`bin/i18n-lint`](../bin/i18n-lint), in the
`lint-guards` CI workflow), which fails on a string literal reaching `textContent`,
`innerHTML`, `aria-label` and friends. Per-line escape hatch for strings that
genuinely should not be translated — staff-only surfaces are the main legitimate
use, and the reason is required and audit-visible (`bin/i18n-lint --show-allows`):

```js
// i18n-allow: /_push-demo/ is a staff-only diagnostic page
$('#push-state').textContent = 'unsupported in this browser';
```

`tests/test_js_strings_are_translatable.py` covers the other half — that every key
a module reads is actually rendered, and every key rendered is actually read. That
pairing fails silently otherwise: the module just serves English forever.

**Adding new strings**: after adding any user-facing string, run:
```bash
uv run python manage.py makemessages -l en --no-location
```

**File tracking**: `.po` files are checked in; `.mo` files are gitignored. We do **not**
run `compilemessages` in CI or on deploy while the catalogue is English-only — every
`msgstr` is empty, so Django falls back to the `msgid` at render time and no compiled
binary is needed. Re-enable the compile step (and install `gettext` on the build
container) when DE/FR/IT translations are added.

**System requirement**: the `gettext` system package is only needed locally for
`makemessages` / `compilemessages` (`brew install gettext` on macOS). Not required for
deploy.
