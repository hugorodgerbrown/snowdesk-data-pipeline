Snowdesk · uploaded routes · how it works

From GPX to line

You choose a file. A moment later there is a purple line on the map and a handful of figures beside it. This page is everything in between — what the file actually holds, which parts we read, what we work out, what we throw away, and what finally gets drawn.

5 MB per file 25 routes each 2,000 points stored, at most the file itself: never kept

Strip the tags away and a GPX file is one simple thing: a list of places, in order. Everything else in it either labels that list or describes the device that recorded it. The whole of what follows is about turning that list into something a map can draw and a person can read.

RULE ONE

Measure first, thin afterwards

The distance, the climb and the drop are worked out over every point of the track we took — all of them, before any are discarded. Only then is it thinned down to the version we store and draw.

Do it the other way round and every route quietly shrinks: a thinned line cuts the corners off, so it is shorter, and it flattens every bump it removes.

RULE TWO

Unknown is not zero

A file with no heights in it produces no climb figure — not “0 m”. A file with no usable times produces no duration.

These are different facts, and the difference matters to someone planning a day out. Everywhere one of them is missing, the app leaves the figure out rather than printing a number it hasn't got.

0

The file arrives

Should we even open this?

Four gates, checked cheapest first, so a hopeless upload never reaches the parser. You must be signed in. You may upload ten files a minute. The file must be under 5 MB — comfortably more than a full day recorded once a second, which comes to roughly 3 MB. And you may hold 25 routes at once; deleting one is what makes room.

The file picker is set to prefer .gpx, but that is a convenience, not a check — an extension is just the end of a name. The only thing that decides whether a file is GPX is whether the bytes parse as XML whose outermost tag is <gpx>.

Parsing goes through a hardened XML reader rather than the standard one. XML has features — external entities, entities that expand into entities — that turn a small file into a tool for reading a server's own files or exhausting its memory. Those are refused by the reader itself, so nothing depends on us remembering to check for them.

What you'd see

  • Not signed inUpload isn't offered at all.
  • Too many, too fast“Please wait before uploading another route.” A minute fixes it.
  • Too largeTold the limit, in bytes, before the file is read.
  • At 25 routesA panel explaining the cap. This one doesn't clear on its own.
  • UnreadableOne fixed sentence: it must be a valid .gpx holding a track or a route.

Why the same message for every bad file. The parser's own complaint names line numbers, and for a hostile file it would echo the attacker's own text back at them. It goes to the log instead. The cost is real: diagnosing a rejected file means asking to see it.

1

Which part of the file we read

A file can hold several paths. Which one is the route?

Three kinds of thing in a GPX file can carry coordinates, and they mean different things. Waypoints (<wpt>) are loose pins — a car park, a hut — with no order and no path between them. A route (<rte>) is a path somebody planned. A track (<trk>) is a path somebody recorded, cut into segments wherever the receiver lost the sky.

We treat a planned route and a recorded track as the same thing — an ordered list of places — because for drawing a line on a map they are. A track wins when a file holds both, since it is the more precise record. Waypoints are ignored entirely, and a file holding nothing but waypoints has no route in it and is refused.

Segments are joined in the order they appear. A break in a recording is a gap in the signal, not the start of a different journey, so stitching them together gives back the single line that was walked.

When a file holds several tracks, the first one wins. The others are counted but not imported, and — today — you are not told. That is a gap rather than a decision, and one we intend to close.

Two tiers of file, and the poorer one is the normal one. Export a course from a planning tool and you get positions and usually heights, but no times — nothing has happened yet. Export an activity from a watch and every point carries the moment it was recorded. Most files that arrive here are the first kind, so everything time-derived has to be an addition to a working untimed route rather than something the app leans on.

Small rules that matter

  • Two versionsGPX 1.0 and 1.1 label their tags differently and some exporters label them not at all. Every lookup matches the short name, so all three work.
  • Each placeLatitude and longitude must both be there, must be numbers, and must be real ones — on the globe, not infinity, not “not a number”.
  • Order flippedStored longitude-first, because that is the order the mapping standard uses and the map expects. Swapping it once, here, means never swapping it again.
  • A bad heightTreated as a gap in the heights, not as a broken file. The point keeps its position.
  • TimesOnly the point's own <time> counts — never one buried in the extras beside it.
  • The nameThe track's name, or failing that the file's; trimmed to 100 characters. If neither names anything, the row falls back to the filename, then to “Untitled route”.
2

The figures, before anything is thrown away

How far, how much up, how much down, how long?

Distance is the sum of the gaps between consecutive places, each measured across the curve of the earth rather than on a flat drawing. It follows the track as recorded, wiggles included.

Climb and drop are read off the heights, in one walk. Every step up is added to one total and every step down to the other, and both come out positive. They are never subtracted from one another: a loop that goes up 800 m and comes back down carries 800 m of each, not nothing. That pairing is the whole point — a there-and-back and a one-way traverse can have the same length and the same climb, and only the drop tells them apart.

Where the heights break off, the walk steps over the gap rather than measuring across it. Two points either side of a missing stretch are not a cliff. And if no point in the file has a height at all, both figures come back unknown.

Duration is the last time minus the first. That is elapsed time, and it counts lunch, the transition and the hour spent digging a pit. Both ends must be present, and the finish must not precede the start; a file timed at one end only, or one whose two ends run backwards, yields no duration rather than half a fact. Only those two stamps are read, so a clock glitch in the middle of a recording passes unnoticed. A file with no times — a planned course, which is the common case — gets no duration at all.

Landing next Moving time. Elapsed is all the app can offer while only the two ends are stored. The next change keeps the whole series: each stored point gains a fourth number, its offset in whole seconds from the start, and a moving duration is summed at upload from the full-resolution track. A stretch counts as stopped when the pace drops below 0.5 m/s and stays there for at least 60 seconds — both conditions, because the 1–5 m of wander a receiver shows at a real stop looks like slow movement on its own, and a genuinely slow climb looks like a stop on the other. An untimed file is unaffected: three numbers per point and no moving time, exactly as now.

Read as a pair

  • 1236 m ↑ / 1239 m ↓A loop. Starts and finishes at about the same height.
  • 1240 m ↑ / 90 m ↓A climb with a lift or a road out.
  • nothing shownThe file carried no heights. Not flat — unrecorded.

Recorded heights are not survey heights. A consumer GPS is poor at altitude, and a barometric watch drifts with the weather. Treat the pair as the shape of the day, not as a measurement. Nothing about the ground — how steep it is, which way it faces — is ever taken from these numbers.

3

Thinning the line

A watch records every second. A screen has a few thousand pixels across. How much of the track do we actually need?

A full day recorded once a second is around 30,000 places — roughly a megabyte of numbers, and far more corners than the line could ever show. So the stored track is capped at 2,000 points.

The thinning uses Douglas–Peucker, the standard line-generalisation algorithm, published in 1973 and still the default in every mapping toolkit fifty years later.1 Its idea is simple: draw a straight line between the two ends, find the point furthest from it, and keep that point only if it is further away than a given tolerance — then repeat on each half. Points that sit close to the line their neighbours already imply add nothing to the shape, so they go. Here it runs through the GEOS geometry library, via shapely's LineString.simplify.

The tolerance is not chosen, it is found: start at about a metre and double it until the track fits under the cap, up to 24 times. If that somehow never arrives — a pathological track of almost-but-not-quite straight points — fall back to taking every nth point, keeping both ends. The cap is a guarantee, not an aim.

Heights are deliberately held back from the geometry handed to the algorithm and reattached afterwards. Douglas–Peucker returns a subsequence of the points it was given — it selects, it never moves anything or invents a vertex — so each survivor can be matched to the original it came from and handed back its own recorded height. That property is also what makes the coming fourth number free: a per-point time rides through the thinning on exactly the same guarantee.

This is the copy that gets stored, drawn and shared. It is also the reason the figures from the previous step are worked out first: this line is shorter than the one that was walked.

What thinning costs

  • ShapeKept. A switchback with 40 recorded points still turns.
  • JitterGone, and good riddance — most of it is receiver noise rather than movement.
  • PrecisionReduced, on purpose. A stored track is location history; less of it is better.
  • TotalsUnaffected, because they were measured before any of this.

Never recomputed downstream. Anything that measured this thinned line would produce a second, slightly smaller set of numbers for the same route — and show them next to the first. So the totals stay the ones taken at upload, and the stored line is used only for its shape.

Both counts are kept

A route with 894 stored points might have been recorded at 894, or cut down from 30,000. Until recently those two read identically in the database, so “is the cap ever actually binding, and on how many routes?” was an argument rather than a query.

Now both numbers are stored: what the file carried and what survived. On any track under the cap they are equal, because the thinning returns a short track untouched. Where they differ, the difference is exactly what was thrown away.

And where they aren't

Routes uploaded before that column existed have no source count, and cannot be given one — the file it would have been read from is long gone. So the column is null for them, which means “we did not record this”, not zero and not “the same as the stored count”. The same contract the climb figure carries.

4

What is stored, and what is gone

Once the row is written, what's left of the file?

Nothing that we keep. The uploaded bytes are read, parsed, and dropped: no copy is stored, in a database, a bucket or a folder, and there is nowhere in the app you could go to download the file you sent. The route you see drawn is the row, not the upload.

One honest qualification, because “never touches disk” would be too strong a claim to make. A small upload is handled entirely in memory, but a larger one — above about 2.5 MB — is spooled to a temporary file by the web framework while the request is in flight, and deleted when the request ends. That is a few seconds of a file we never asked for and never read twice. What the paragraph above rules out is a retained copy, and that part is absolute.

That is a deliberate choice rather than an oversight. This project stores no files at all: everything it serves is either a fixed asset or a database row. Keeping the originals would mean adding file storage, credentials, a retention policy and a deletion path that stays in step with deleting a route — worth doing when something needs it, and nothing does. A GPX track is also location history, and the less of it kept, in the fewer places, the smaller the exposure.

The cost is real and worth stating: a route already imported can never be re-read under better rules. A parsing improvement applies to new uploads only, and re-uploading the file is the only remedy. It is also why a column added late can sometimes be backfilled and sometimes not — anything recoverable from the stored points can be, and anything that was only ever in the file cannot.

And back out again

A stored route can be written back out as a .gpx. It is an internal tool today — one route at a time, not something you can reach from the app — and it exists because a stored route is otherwise a database row, and getting one into anything that understands tracks meant writing a converter by hand.

What comes out is a reconstitution, never the original, and the file says so in its own description field rather than leaving a reader to find out. Three things differ, each for a reason already established above: no point carries a time, because only the two ends are stored and inventing a pace the recording never had is not on; the geometry may be the thinned line, with both point counts named in the description so a reader can tell a 894-point recording from a 894-point remnant of 30,000; and the totals are left out of the file entirely, because they were measured on the full track and a reader who recomputed them from what is there should get that track's own figures rather than a mixture.

What the file says about itself

Reconstituted from Snowdesk stored points (route …). The uploaded file was parsed and discarded at ingest; this is not it. 894 points stored, simplified from 30,412 in the source file. Per-point timestamps are not stored and are absent here.

Heights are left out, not defaulted. A point whose height was never recorded is written without one. A zero would put the track at sea level; the neighbouring value would invent terrain. The same refusal the profile chart makes when it breaks the line instead of bridging it.

5

What gets drawn

How does a list of coordinates become something you can see and tap?

The stored coordinates go to the map exactly as stored. They were saved in the order the mapping standard uses, which is the order the map expects, so nothing is rearranged on the way out and there is no opportunity for a swap to creep in between the two.

The line is drawn twice: a wide pale casing underneath and the route colour on top. That is what keeps one colour legible over both a white winter basemap and a dark satellite one. Both widths grow with zoom, so the track is a hairline at country scale and something you can follow in a valley.

From zoom 10 the ends are marked — a filled dot where the track starts, a chequered flag where it finishes. A line says where you went but nothing about which way round; these say it without a legend.

A route somebody shared with you is drawn dashed, in a different colour, and on top. Both differences are deliberate: the dash carries the meaning for a colour-blind reader, the colour carries it at a zoom where a dash is too small to see. A route you own and a route you have been sent support different actions, and the map has to say which is which before it is tapped.

Tapping flies the map to the route's stored rectangle and opens the detail sheet docked below it — the same sheet the rest of the map uses. It was an anchored popup until recently, and a 320-pixel card had stopped being enough for what there is to say about a line.

The sheet holds the name, then the length, climb and drop — each omitted entirely if it isn't known — then the height profile, then the low-to-high range and the elapsed time. For a route of your own, below that sits the one thing the popup had no room for: what the day's bulletin says about this particular line, fetched for whatever date the map is showing and re-fetched when you move the scrubber. A route somebody has shared with you does not carry it until you save it — an unclaimed share is identified by its link rather than by a route of yours, and the reading is looked up per route. That half belongs to the terrain story rather than this one.

The profile

The chart is drawn from the third number of every coordinate the map already holds. It needs no second request, and because the routes layer is cached on the device, it draws offline too.

It shows the heights the file recorded and nothing else. No smoothing, no terrain lookup, and — the important one — no bridging a gap: where the heights break, the curve breaks. A plausible straight line across missing data is the same class of error as reporting 0 m of climb for a track that recorded none.

The chart and the figures come from different copies. The curve is shaped by the stored line; the totals printed beside it were measured on the full one. The lowest and highest points are honest either way — thinning can drop a point, but it cannot invent a summit that was never recorded.

The ground, and what you were doing on it

Everything above is about the track: a list of places somebody recorded, and the few figures that follow from it.

It says nothing about the terrain the track crosses — how steep the mountain is there, which way the slope faces, where the fall line runs, which passages have steep ground hanging above them.

That is a separate pipeline with one firm rule: steepness is read from the ground, never from the file. A skin track zig-zagging up a 38° face climbs about 15° along its own length, and a traverse across the same face climbs almost nothing. Colour a line by its own gradient and a serious slope looks easy.

Reading the track as an activity — where you were climbing, descending or crossing — is a further step again, and it needs both halves: the direction of travel along the track and the direction the slope faces.

Both are for a later page. The layers they produce are taken apart in Anatomy of a Route.

Which side of the wire each step happens on

Everything that interprets the file happens once, on upload, on the server. Everything that draws happens on your device — which is what lets a saved route still work when there is no signal.
