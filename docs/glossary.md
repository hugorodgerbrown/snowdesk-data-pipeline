# Glossary — domain terms to code symbols

One line per term: what it means here, and where it lives in code. When a doc,
a template, and a conversation use different words for the same thing, this
file states the canonical name. Update it whenever a new domain term acquires
a code symbol.

## Formats and sources

| Term | Meaning | Code |
|------|---------|------|
| CAAML | Open avalanche-bulletin interchange standard ("CAA Markup Language"); this project consumes **CAAML v6 JSON** | consumed throughout `apps/bulletins/` |
| SLF | Swiss Institute for Snow and Avalanche Research — primary provider | `apps/bulletins/services/slf_fetcher.py` |
| ALBINA | EUREGIO (Tyrol/South Tyrol/Trentino) avalanche service | `apps/bulletins/services/albina_fetcher.py` |
| Météo-France | French provider; serves DPBRA XML, not CAAML | `apps/bulletins/services/meteofrance_fetcher.py` |
| DPBRA | Météo-France's public avalanche-risk-bulletin product (XML, one document per massif) at `public-api.meteofrance.fr/public/DPBRA/v1/` | translated to CAAML v6 JSON by `apps/bulletins/services/meteofrance_translator.py` |
| Source | The provider a bulletin was ingested from, stored on the indexed `Bulletin.source` column and named by the `Bulletin.Source` TextChoices — `"SLF"`, `"ALBINA"`, `"METEOFRANCE"` (upper-cased by SNOW-582). Set at ingest by `upsert_bulletin` from `detect_source`, never read back out of `render_model["source"]` | `apps/bulletins/models.py`; backfilled by `backfill_bulletin_source` |
| Fidelity | The rule that every field the provider published reaches a rendered surface, and anything excluded carries a written reason. One row per dotted CAAML path across the nine sentinels | `tests/sentinels/fidelity.py` (`Rendered` / `Excluded`), checked by `bin/fidelity-lint` and `tests/sentinels/test_fidelity.py` |
| GeoJSON Feature envelope | Raw bulletins are stored wrapped as `{type: "Feature", geometry: null, properties: <raw CAAML>}` | `upsert_bulletin()` in `apps/bulletins/services/slf_fetcher.py` (shared by all fetchers) |
| EAWS | European Avalanche Warning Services — defines the region hierarchy and the 1–5 danger scale | `apps/regions/fixtures/eaws_{CH,AT,FR,IT}.json` |
| Massif | Météo-France's mountain-region unit (e.g. `CHABLAIS`); slug → `FR-NN` region id | `apps/bulletins/services/meteofrance_massifs.py` (`SLUG_TO_CODE`, `slug_to_region_id()`) |

## Regions

EAWS hierarchy: L1 (`MajorRegion`) → L2 (`SubRegion`) → L4 (`MicroRegion`);
L3 is deliberately skipped. All in `apps/regions/models.py`.

| Term | Meaning |
|------|---------|
| MajorRegion | L1, e.g. `CH-4` (Valais); `prefix` unique, boundary derived from children |
| SubRegion | L2, e.g. `CH-41` (Lower Valais); FK to major |
| MicroRegion | L4 warning region, e.g. `CH-4115` or `FR-68` — the unit bulletins, ratings, and subscriptions attach to; `region_id` unique |
| Resort | Ski resort geocoded onto a MicroRegion |
| Region id formats | `CH-4115` (4-digit), `FR-01` (2-digit), `AT-07-23-02` / `IT-32-BZ-15` (multi-level) |
| Resort page | Public detail page for one Resort at `/resorts/<slug>/` — danger chip, bulletin link, favourite toggle (SNOW-504); the pre-slug `/resorts/<id>/<slug>/` form is a permanent redirect (`public:resort_legacy`, SNOW-796). `public:resort` route; `resort_detail()` in `apps/public/views.py`; template `apps/public/templates/public/resort.html` |
| RegionAlias | A hand-curated alternate name for a MicroRegion — an exonym pair sharing no letters ("Sitten" / "Sion") that fuzzy matching cannot bridge; feeds the MCP place search only. `RegionAlias` in `apps/regions/models.py`; `apps/regions/fixtures/region_aliases.json`; `search_places` in `apps/mcp_server/resolvers.py` |
| Neighbour | The explicit through row of `MicroRegion.neighbours`, the self-referential M2M of regions sharing a boundary. `MicroRegionNeighbour` in `apps/regions/models.py` |
| Resort editor | The superuser-only in-map editing of resorts and curated locations — a queue of rows, save, create, link/unlink. Gated by an ordinary `is_superuser` check, not a flag (SNOW-724). `api:edit_resorts_queue` / `edit_resort_save` / `edit_locations_queue` … with `_require_edit_map_admin` in `apps/public/api.py`; `static/js/map_edit_resorts.js` / `map_edit_locations.js`; [resorts-are-editable-data.md](decisions/resorts-are-editable-data.md) |
| Resort tier | Curated map prominence for one resort — `CORE` / `STANDARD` / `MINOR`, driving pin radius on the map (SNOW-543). Stored, not derived: scale is the wrong axis, so a curator can promote a small high area. `Resort.Tier`; sheet column `tier`; `properties.tier` on `/api/resorts.geojson`; consumed by `installResortsLayer` in `static/js/map.js` |
| Why it matters | One curated sentence on why a backcountry skier should care about a resort — terrain, access, reputation; the thing piste km cannot say (SNOW-542). `Resort.why_it_matters`; sheet column `why_it_matters`; rendered by `apps/public/templates/public/partials/_resort_why_it_matters.html` |

## Routes

| Term | Meaning | Code |
|------|---------|------|
| Route | A polyline a user imported from a GPX upload (SNOW-685) — `points` as `[[lon, lat, ele], …]` in GeoJSON axis order, plus denormalised `distance_m` / `ascent_m` / `descent_m` / `point_count` / `bounds`. The uploaded file is parsed and discarded ([why](decisions/gpx-uploads-are-parsed-not-stored.md)) | `apps/routes/models.py`; ingest in `apps/routes/services/gpx.py` |
| RouteShare | A tokenised link handing one Route to another account (SNOW-764). Reusable and time-bounded (`settings.ROUTE_SHARE_MAX_AGE_DAYS`); claiming it COPIES the route onto the claimer's account and never transfers it, so the sharer keeps theirs | `apps/routes/models.py`; `apps/routes/services/shares.py` |
| Pending share | A `RouteShare` this browser has followed but not claimed. Held as a token in `request.session["route_shares"]`, which is why the routes panel and the routes map layer answer for an anonymous request ([why](decisions/route-share-pending-claim-in-session.md)). Drawn as the dashed `routes-line-pending` layer | `pending_shares()` in `apps/routes/services/shares.py`; `routes-line-pending` in `static/js/map.js` |
| Route detail panel | What a tap on a saved route's line opens — the docked sheet (`#route-detail-sheet`) opened from the rail's "Terrain" menu item since SNOW-1018, carrying the route's terrain lines. It also held a reading of the day's bulletin until SNOW-1062: the day's danger is a map layer (SNOW-979), not an attribute of a route. An anchored MapLibre popup until SNOW-973, which moved it out of the shared `.detail-popup` chrome the resort and favourite pins still use once five tickets of terrain reading had outgrown a 320px card | `apps/public/templates/public/partials/_route_detail_sheet.html`; `static/js/map_route_detail.js` (`window.pwaRouteDetail`); `activateRoute` in `static/js/map.js` |
| Elevation profile | The chart of a Route's height against distance along it, drawn on the rail since SNOW-1018 (the route detail panel until then; the rail is pinned top-left since SNOW-1068). Read from the third ordinate of the feature's coordinates — since SNOW-1043 the terrain track, whose heights are the terrain model's wherever the slope record has them and the device's `<ele>` elsewhere — with no smoothing and no interpolation across a point whose height is missing (the line breaks instead) | `static/js/elevation_profile_core.js`'s `readProfile`; the coordinates are `terrain_points` in `apps/routes/views.py`; drawn per leg by `legPaths` in `static/js/route_rail_core.js` |
| Start / finish markers | The two symbols at a Route's ends on the map — a filled dot in the route colour where the track starts, a checkered flag where it ends. Shown from zoom 10, matching the resort labels. A closed track (an out-and-back) gets the flag alone, since both ends are the same place | `static/js/route_markers_core.js`; the `routes-endpoints` layer in `static/js/map.js` |
| Leg | A stretch of a Route that is consistently climbing or consistently descending — the run between two transitions. A transition is found where SMOOTHED elevation changes sign and then moved onto the raw high or low point within the smoothing window, so a climb ends on its summit. `Leg.climbing` is the only direction it carries: the activity is an inference on top of it and is deliberately not made here, because nothing in `points` separates skinning from bootpacking. Derived on every read from `points` alone — no DEM, no network, no stored column — so it works offline and costs microseconds. The smoothing window is in METRES rather than in points, because a point is a position fix at whatever interval the device chose, and the same setting would otherwise smooth away a roll on one track while preserving it on another (SNOW-990) | `Leg` / `detect_legs` in `apps/routes/services/legs.py`. On the wire as `legs` on the routes feature, in SAMPLE indices plus `point_from` / `point_to` into the coordinates (`wire_legs` in `apps/routes/services/leg_wire.py`), drawn by the rail (SNOW-1018) and on the map as one line per leg (`static/js/route_legs_core.js`, SNOW-1017). The feed cuts them from `terrain_points`, so the heights they read are the terrain model's where the slope record has them (SNOW-1043) |
| Transition | Where one Leg ends and the next begins — the point at which the route stops climbing and starts descending, or the reverse. N − 1 of them for N legs. A skier changing from skins to boots mid-climb crosses no transition, because the service reads height and not activity | The boundary between consecutive `Leg` runs; `_runs` / `_merge_short_runs` / `_snap_to_extrema` in `apps/routes/services/legs.py`; [a-leg-transition-sits-on-the-extremum.md](decisions/a-leg-transition-sits-on-the-extremum.md). Drawn on the map as a numbered circle (`transitionCollection` in `static/js/route_legs_core.js`, SNOW-1017) |
| Rail | The route panel, pinned top-left while a route is open (under the region chip's row on desktop, on the top edge on a phone, SNOW-1068), carrying a route unrolled against distance along it: the route's name as title, the routes list's meta line ("12.9km · 337m ↑ · 1906m ↓ · 2h51m", time only when the recording has one) as subtitle, then the height profile filled per leg, with a "…" menu and × top right. One column at every width — `--route-column-width`, 400 px on desktop, full width less insets on a phone, left-aligned. Its header is the route's, the open leg's, or a placed point's (the point header, see Point card); the × clears a placed point before it closes the route. The map answers where the route goes; the rail answers what is along it, and the two share one cursor position. Pressing a leg highlights it on the map and profile (the others dimmed), adds "• Leg 3" to the title (`[data-route-rail-leg]`) and swaps the subtitle for that leg's figures — gross ascent and descent, no time; pressing it again closes it. A drag of more than 6 px along the lane places a point; a press without movement presses the leg. A tap on the map that no marker takes, while a route is open, closes the rail. SNOW-1065 deleted the second row that used to sit under it (rail two) | `templates/includes/_route_rail.html`; `static/js/route_rail_core.js` (tick step, one fill per leg, `formatMetaLine`, `formatDuration` — mirroring `split_hours_minutes` in `apps/core/durations.py` — and `legFigures`) and `static/js/route_rail.js` (`window.pwaRouteRail`); `--route-column-width` in `static/css/map.css` |
| Cursor | The one place a reader is pointing at on a route, shared by the map, the rail and its point header. Keyed on the SAMPLE INDEX — an integer into the slope record's segments — never on a distance, because the profile's distance and the sampler's distance disagree by a chord per switchback. Each surface converts its own geometry to an index and back. Holds a leg or a point, NEVER BOTH (SNOW-1065): `openLeg` clears the index and `setIndex(n)` clears the open leg. A mouse hover over the rail's lane or the map's route line moves the point only while no leg is open; a drag along the lane places one with any pointer; a tap on the open route's line places the point and no longer opens a leg. Read by the rail (a line on the profile, and its point header), the map (the dot, every leg but the open one dimmed) | `createRouteCursor` in `static/js/route_cursor_core.js` (SNOW-1016); the map's placing in `static/js/route_cursor_map_core.js` and `bindRouteCursor` in `static/js/map.js` |
| Ascent / descent | A Route's total climb and total drop in metres, both positive magnitudes, measured independently at ingest on the full-resolution track and never netted against each other. Null — not zero — when the source GPX carried no elevation at all | `Route.ascent_m` / `Route.descent_m`; `_total_ascent_descent_m` in `apps/routes/services/gpx.py` |
| Key passage (crux) | REMOVED (SNOW-1066). SNOW-911 flagged a stretch of track where the ground above the skier was steep enough to release a slab; Snowdesk no longer keeps a route-level crux. Where the dangerous ground is is decided by the daily avalanche terrain layer (SNOW-979). Records sampled before SNOW-1066 may still hold a `cruxes` key and per-segment `crux` flags; nothing reads them and the wire never sends them | None — `apps/routes/services/cruxes.py` was deleted. See SNOW-979 for the avalanche terrain layer |
| Canonical tours | The committed corpus of real GPX tracks — four today — that every route threshold is tuned and tested against, read through `parse_gpx` like any upload (SNOW-989); `seed_test_data` and `seed_canonical_routes` load them as the dev user's routes | `apps/routes/fixtures/canonical/`; `canonical_documents` / `recording_documents` in `apps/routes/services/canonical.py` |
| Download area | The DEFINITION of one offline basemap download on a user's account (SNOW-749) — a region id or a `[west, south, east, north]` bbox, plus the basemap key and a name, keyed by the client-minted `area_id` that also names the device's Cache Storage bucket. Never the bytes: those are per-browser, so an area on this list is not thereby available offline here | `apps/downloads/models.py` (`DownloadArea`); client in `static/js/downloads_sync.js`, merged by `reconcileAreas` in `static/js/basemap_manage_core.js` |
| Permanent / perishable half | The two halves of a downloaded area, which age differently (SNOW-924). The PERMANENT half is the tiles, style, sprite, glyphs and slope raster — a fixed grid over fixed ground, fetched once. The PERISHABLE half is the bulletins, weather and observations inside the boundary, which are new every day and are what a refresh tap re-fetches | `contentUrls` in `static/js/basemap_download_runner.js`; `assembleAreaContentURLs` in `static/js/map_basemap_downloads.js` |
| `contentAt` | When an area's perishable half was last fetched in full, stored beside `savedAt` on its `meta:app` record. Absent means never — every area downloaded before SNOW-924 — and is read as "not yet" rather than as a fault, since the tiles are the half that decides whether a map draws | `_recordRegionDownload` / `_stampRegionContent` in `static/js/map_region_download.js` |
| `partial` (roundel state) | A download run where one half landed and the other did not. Amber, and its remedy is the same refresh tap. Deliberately a run OUTCOME and never derived from a missing `contentAt`, which would paint a warning over every area downloaded before SNOW-924 | `static/js/map_region_download.js`; `static/css/map.css` |
| `onDevice` / `synced` | The two independent facts every reconciled download area carries. `onDevice` means the tiles are in this browser's Cache Storage; `synced` means the account has a `DownloadArea` row for it. They are separate because "in your account" is not "available offline" — a synced-not-here area must never paint a green sync dot | `reconcileAreas` / `manageRows` in `static/js/basemap_manage_core.js` |

## Trips

| Term | Meaning | Code |
|------|---------|------|
| Trip | A route the organiser already owns, on a named day, meeting somewhere at a stated time (SNOW-819). One row with a roster, never a thing that gets copied — everyone on it is meeting each other, so they belong on the same row ([why](decisions/a-trip-is-one-object-with-a-roster.md)) | `Trip` in `apps/trips/models.py`; `create_trip` in `apps/trips/services/trips.py` |
| Trip snapshot | The route geometry and figures COPIED onto a `Trip` at creation and never re-read — `points`, `bounds`, `distance_m`, `ascent_m`, `descent_m`, `duration`, `point_count`, `route_name`. It is what makes a trip survive the organiser renaming, re-uploading or deleting the route it came from | `Trip.points` and siblings; `_SNAPSHOT_FIELDS` in `apps/trips/services/trips.py` |
| Organiser | The account that created a trip. Derived from `Trip.created_by`, never a second column on the roster row — they hold a `TripParticipant` row like everybody else, so "everyone on this trip" is one relation | `Trip.created_by`; `is_organiser` in `apps/trips/views.py` |
| TripParticipant | One account that has SAVED one trip. `(trip, user)` is unique, and the organiser's row is written at creation. Written by "Save this trip" and removed by "Remove from my trips" (SNOW-848 relabelled SNOW-822's join/leave); no surface states how many rows a trip has, or whose ([why](decisions/a-trip-is-one-object-with-a-roster.md)) | `TripParticipant` in `apps/trips/models.py` |
