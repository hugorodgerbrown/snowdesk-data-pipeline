Snowdesk · command audit

Fifty commands, and which ones still earn their place

Every custom manage.py command in the pipeline — what it does, when it should run, and whether it is still required. Seven run themselves. Eleven are finished work waiting to be deleted.

2026-09-15 snowdesk-data-pipeline 50 commands · 14 apps all documented · all tested
7 Run without a human — five on the scheduler, one on deploy, one worker entry point
27 Operator tools, fixture builders and diagnostics, run on demand
5 One-shot backfills still load-bearing or re-armed by later tickets
11 Spent one-offs — deletable once confirmed run in production

Scheduled — 5

All five exit non-zero on failure, so a missed run shows up in the worker log rather than passing silently.

fetch_bulletins
Fetches CAAML bulletins from SLF, ALBINA and Météo-France and upserts them; walks from each source's latest stored day, so a missed run self-heals on the next one.
Hourly, :00 and :05 UTC
Required
fetch_weather
Writes today's Open-Meteo forecast row for every active Location.
00:00 · 06:00 · 12:00 · 18:00 UTC
Required
Four passes because a location has no on-demand fetch behind its page render the way a bulletin region does — this batch is the only thing keeping today's row current.
purge_request_logs
Deletes RequestLog rows past the twelve-month retention window.
Daily, 03:30 UTC
Required
Enforces a promise the Privacy Policy already makes. Deliberately on the half hour, on an hour no fetch uses: it holds a delete transaction over a table the request path writes to.
fill_what3words
Converts each Location still lacking a three word address.
Daily, 04:00 UTC
Required
A clean no-op when no API key is set, which is what lets it be registered unconditionally.
link_resort_locations --check
Reports geocoded resorts carrying no ResortLocation — each one a resort page rendering no Forecasts section with nothing saying so.
Daily, 05:00 UTC
Required
The only scheduled job that writes nothing. The response is an operator running --commit by hand; PR #758 took that write off the deploy path on purpose.

Drift found, and fixed

One deploy change in PR #758 — taking every bulk data write out of build.sh — left five statements across the codebase describing a deploy that no longer happens. All five are corrected in this commit.

compute_basemap_download.py + docs/management-commands.md

Said"Wired into build.sh's post-deploy step, alongside the other derived-data commands" — and, in the catalogue, "build.sh runs it with --commit on every deploy (SNOW-521), after the loaddata step above."

Neither is true. build.sh names the command only inside the comment block explaining that all three bulk-write steps were removed. Nothing computes these blobs on deploy, and nothing said so — which matters, because a stale blob is an offline map that silently under-covers. Both now say an operator runs it.

refresh_centroid_elevations.py

Said"bin/build.sh reloads these fixtures on every deploy … link_region_centroid_locations becomes a pure offline derivation that build.sh can re-run immediately after loaddata, on every deploy, for free."

The whole rationale for storing the elevation in the fixture was written in the present tense about a self-healing deploy step that has since been deleted. The elevation still belongs in the fixture — it is what keeps the re-link offline — but the reason now has to be stated without the deploy.

MicroRegion.centroid_location help text

Said"Derived, NOT durable … loaddata resets it to NULL every time. Never treat a value here as surviving a deploy."

Read by whoever opens the region in the Django admin, and now exactly backwards: the column is durable, because no deploy loads a fixture any more. Corrected, with a migration for the changed help text.

locations/services/anchor.py + the location-migration runbook

Said"bin/build.sh reloads the EAWS fixtures on every deploy … wiped and re-linked on each deploy" — and, in the runbook, that SNOW-771 was "fixed by making build.sh re-link after every loaddata."

That was the first patch; PR #758 then removed the reload itself. The reuse rule the service exists to enforce still holds for the same reason — an operator's re-run must rebind to the surviving row rather than strand it and its weather — so the rationale is rewritten rather than dropped.

Method. Every one of the 50 command modules read in full, against docs/management-commands.md, schedule.py, bin/build.sh and bin/init-worktree. Retirement calls rest on a command's own stated purpose being finished, not on production state — each is conditional on confirming the command has run in every environment, which a read-only invocation reporting zero rows will settle.

No command is undocumented and none is untested: all 50 carry a catalogue entry and at least one test module. The audit found no shape violations against the five management-command design rules — only the drift above.
