# JavaScript review — 2026-08-03

Scope: 35 first-party modules in `static/js/` (~23k lines) plus inline `<script>`
blocks in `templates/**` and `apps/*/templates/**`. Vendored files
(`htmx.min.js`, `maplibre-gl.min.js`) excluded.

## State of the codebase

Three things are working.

**The extraction pattern is real and it is used.** `scrubber_core.js`,
`mutation_queue_core.js`, `basemap_cache_core.js`, `basemap_download_core.js` and
`basemap_manage_core.js` each pull pure logic out of a page or worker module,
attach to `self` so both contexts can reach them, and carry a passing Vitest
suite. Where that pattern has been applied, the logic is tested and the
duplication is gone. The gaps below are places it has not been applied yet, not
places it failed.

**The documentation is dense and mostly load-bearing.** Several duplications
this review found were already documented, with the reason, at the site — the
four-way pinned-cache prefix (`basemap_download_core.js:235-250`), the
worker-side DB open (`sw.js:1646-1661`), the per-page passkey divergence
(`setup.html:100-104`). Reviews that assume undocumented drift keep being wrong
here. Where the comments have gone stale, that is now the defect, and there are
three clear cases.

**Progressive enhancement mostly holds, and e2e coverage is broader than it
looks.** Several suspected gaps turned out to be pinned — the script load order
by `tests/e2e/test_pwa_client_signals.py:444`, the geolocate event contract by
`tests/e2e/test_community_reports.py:379`, the inline share block by
`tests/e2e/test_share_button.py`. One core control is genuinely JS-only.

Three systemic problems.

**1. Cross-script coupling has no manifest, and every read is guarded, so a
wrong name never surfaces.** 20 `window`/`self` exports, 30 `snowdesk:*` custom
events and 75 optional-chained global reads communicate across plain
`<script src>` tags. The convention is that a missing dependency degrades
silently. The demonstrated cost is `window.MAP`: it has never existed, has been
read for its whole life, its consumer silently returns the wrong answer, and its
unit test manufactures the property under jsdom. Nine `eslint-disable` comments
sit in the tree with no linter behind them.

**2. `map.js` is 8,165 lines, and its internal duplication is a symptom of
that.** The file already contains 11 clean IIFE seams. Inside it: two ~600/1000
line download-control IIFEs with five parallel members each, three copies of the
choropleth paint loop, three declarations of `OVERLAY_STORAGE_KEY`, and the
pinned-cache read written twice. None of that would survive if the units were
separate files.

**3. Failure is silent by default.** Roughly 200 catch blocks swallow without
logging. Combined with the guarded-global convention, most defects in this
document fail with no console output, no telemetry and no test failure — the
mutation queue burns its retry budget offline, the reset path reloads into the
overlay it was meant to clear, a partially-failed download strands quota with no
record, and a stale flag re-fetches a hidden layer forever.

By dimension: **duplication** is the noisiest category but mostly bounded and
often deliberate — four sharp cases carry real cost, the rest is cleanup.
**Performance** is largely clean; four genuine issues, all with a named
mechanism and a small fix, and several plausible-looking ones that do not
survive measurement. **Maintainability** carries the weight, and holds all four
live bugs.

## Duplicate code

### D1 — Two download-control IIFEs, drifted; the region path evicts, then aborts **[BUG]**

`mapDownloadControlInit` (`static/js/map.js:6089-6683`) and
`mapCustomDownloadControlInit` (`static/js/map.js:6755-7763`) carry five
parallel members each: `_probeDone` (`map.js:6299` / `map.js:6801`), `setState`
(`map.js:6334` / `map.js:6819`), `_retryWhenStyleSettles` (`map.js:6401` /
`map.js:6861` — byte-identical 9-line bodies), `renderControl` (`map.js:6425` /
`map.js:6878`) and the download run (`handleClick` `map.js:6487-6643`, 157 lines
/ `handleConfirm` `map.js:7553-7717`, 165 lines). The two run bodies share an
ordered sequence — offline guard, `clearBasemapDownloadError()`, `setState('busy')`,
quota check, budget plan, eviction, tile plan, progress grid, `onProgress`,
`finish` — ending in the byte-identical dispatch at `map.js:6639` and
`map.js:7713`.

They have drifted on pre-flight ordering, and the drift destroys data. The
custom-area control checks `if (!core || !template)` at `map.js:7595`, **before**
its eviction at `map.js:7621`. The region control evicts at `map.js:6533` and
does not reach the same guard until `map.js:6560`, with a blob fetch that can
also bail at `map.js:6543` in between. `evictBasemapAreas` (`map.js:357`)
permanently deletes another area's pinned Cache Storage bucket and its
`meta:app` record. So a user who confirms "evict area X to make room" can lose X
at `map.js:6533` and then have the run abort at `map.js:6543` (blob fetch fails)
or `map.js:6560` (style still settling) with `setState('error')` and no download
attempted. The fix landed in one copy only.

Fix the ordering first — move the `!core || !template` check and the blob fetch
ahead of `confirmBasemapEviction`/`evictBasemapAreas` in the region path. Then
extract one `runPinnedDownload({ areaId, mb, blob, template, setState, onRecord })`
and one shared `retryWhenStyleSettles(render)` beside the existing
`planBasemapDownloadBudget`/`evictBasemapAreas` helpers.

### D2 — `drain()` is missing the `navigator.onLine` guard `flush()` has **[BUG]**

`mutation_queue.js`'s `_wireLifecycle` (`static/js/mutation_queue.js:740-772`) is
a declared copy of `telemetry.js`'s (`static/js/telemetry.js:432-476`) — the
module header says so at `mutation_queue.js:48`. The copies diverge on the
offline guard. `telemetry.js:372-374` opens `flush()` with
`if (typeof navigator !== 'undefined' && navigator.onLine === false) return Promise.resolve();`
and a comment explaining that the POST can only fail. `drain()`
(`mutation_queue.js:594-640`) has no such check. `enqueue()` at
`mutation_queue.js:578` does check `navigator.onLine`, so the guard was known to
be needed — but the three lifecycle triggers (`online` `mutation_queue.js:745`,
`visibilitychange` `mutation_queue.js:752-757`, the 30s interval
`mutation_queue.js:761-765`) all call `drain()` unconditionally.

Non-GET requests classify as `'network'` (`sw.js:875`) so the service worker does
not intercept a replay POST; `fetch` rejects, `_processRow`
(`mutation_queue.js:510-512`) classifies `'retry'`, and `attempts` increments at
`mutation_queue.js:523`. Backoff is `min(2^attempts, 300)` seconds, so roughly
70 minutes of foregrounded offline use drives a queued row from 0 to
`MAX_ATTEMPTS = 20` (`mutation_queue_core.js:53`), at which point
`mutation_queue.js:531-534` marks it `failed`, fires the permanent-failure toast
and never retries it. A field observation or offline favourite queued at a
trailhead is stranded before the user reconnects. That is well inside a normal
day's touring, and no test drains while offline — every `onLine: false` block in
`tests/js/test_mutation_queue.js` flips back to true before calling `drain()`.

The second drift in the same mirrored pair: `telemetry.js:465-475` has a
`pagehide` keepalive flush; `_wireLifecycle` has none.

### D3 — `sw.js` keeps inline duplicates of eight core-module functions; `worseReason` has drifted **[BUG, latent]**

Every `importScripts`'d helper in `sw.js` is a delegator with a hand-copied
inline fallback, reachable because both imports are wrapped in try/catch
(`sw.js:195-203`, `sw.js:211-216`): `_classifySync` (`sw.js:866` vs
`basemap_cache_core.js:83`), `_classifyCrossOriginGet` (`sw.js:908` vs `:109`),
`shouldPersist` (`sw.js:990` vs `:146`), `_trimCache` (`sw.js:1029` vs `:120`),
`_warmCacheRunPool` (`sw.js:1067` vs `:184`), `_warmCacheClassifyFailure`
(`sw.js:1082` vs `:218`), `_warmCacheWorseReason` (`sw.js:1098` vs `:238`),
`_warmCacheResponseBytes` (`sw.js:1115` vs `:269`), plus a four-function inline
copy of `mutation_queue_core.js` in `_selfDrainMutations`
(`sw.js:1731-1743`). Roughly 90 lines across nine sites.

One has diverged in substance. `sw.js:1101` is `return a || b || null;` while
`basemap_cache_core.js:238` ranks by
`REASON_PRECEDENCE = ['quota', 'network', 'other']`. So
`worseReason('network', 'quota')` returns `'quota'` in the core and `'network'`
in the fallback: on the degraded-startup path, a download that hits a
storage-quota failure among network failures tells the user "network error"
instead of "storage full" — the one reason with a distinct remedy and the only
one that will not succeed on retry. `tests/js/test_basemap_cache_core.js:326-345`
covers the core; nothing covers the fallback.

Separately, the mutation drain loop itself exists twice in full —
`_processRow` + `drain` (`mutation_queue.js:468-640`, ~110 lines) and
`_selfDrainMutations` (`sw.js:1727-1866`, ~140 lines) — sharing the principal
guard, header assembly, success/permanent/retry branches and backoff write-back.
`sw.js:1839-1844` omits `attempts` from the `max_attempts`
`pwa.mutation.failed_permanent` payload that `mutation_queue.js:435-441` includes
and `docs/mutation-queue.md` promises; the `permanent_4xx` branch at
`sw.js:1815-1827` does include it, so the gap is narrow.

Preferred fix: delete the inline fallbacks and let a failed `importScripts` be a
hard error — a 404 there means the deploy is broken. If the fallbacks stay, fix
`sw.js:1101` to mirror `REASON_PRECEDENCE` and add a Vitest case asserting both
implementations agree on a shared input table. The drain loop itself is
reducible by moving the per-row transition into `mutation_queue_core.js` as
`(row, outcome, now) -> {action, row, telemetry}`, leaving each caller its own
I/O.

`sw-kill.js`'s activate (`:50-119`) runs in a worker global with no `window` or

## Performance

### P1 — The service worker enumerates the whole basemap cache after every tile response

`_basemapStaleWhileRevalidate` (`sw.js:1357`) awaits
`_trimCache(cache, BASEMAP_CACHE_MAX_ENTRIES)` at `sw.js:1364` after every
successful cross-origin response. `trimCache`
(`basemap_cache_core.js:120-125`) unconditionally runs `await cache.keys()` at
`:121` before discovering `excess <= 0` at `:122`.
`BASEMAP_CACHE_MAX_ENTRIES = 600` (`sw.js:430`). Every cross-origin GET to a
registered basemap origin routes here — `_classifyCrossOriginGet`
(`sw.js:905-913`) classifies by origin with no path filter, so tiles, sprites
and glyphs all land on it.

Once the cache reaches its cap, each response pays an O(600) enumeration —
constructing and marshalling ~600 `Request` objects into the worker heap — to
delete about one entry. A put can breach the cap by at most one, so the check is
knowable without the scan. On a cache hit `sw.js:1369` returns before the trim,
so served-from-cache tiles are unaffected. On a **miss** — panning into new
terrain — `sw.js:1389` does `await fetchPromise`, and `fetchPromise` only settles
after put and trim, so the enumeration sits directly between the network response
and the tile reaching MapLibre. A pan loading 20-30 tiles is 12,000-18,000
`Request` marshalls on the single worker thread that is also answering the next
`respondWith`.

Fix: maintain a counter and trim once every N puts (down to `MAX - slack`), or
debounce the trim to idle.

### P2 — Offline tile reads scan every pinned bucket serially, re-listing all caches per request

On a `BASEMAP_CACHE` miss, `sw.js:1374` calls `_pinnedCacheNames()` then loops
the buckets with `await caches.open(name)` + `await pinnedCache.match(request)`
sequentially (`sw.js:1375-1379`). `_pinnedCacheNames` (`sw.js:476-481`) runs
`caches.keys()` on every call and is deliberately not memoised (docstring at
`:469-472`).

This is the hot path for the feature the subsystem exists for. `_warmCache`
writes pinned tiles only into their own bucket (`sw.js:1204-1206`, `:1276`), and
`BASEMAP_CACHE` is capped at 600 entries while a downloaded area holds far more —
so browsing offline over downloaded terrain misses the passive cache on
essentially every tile and pays one `caches.keys()` plus up to N serialised

Fix: memoise the bucket-name list (invalidated from the page's eviction path,
which already messages the worker), hold the opened `Cache` handles for the
worker's lifetime, and run the matches with `Promise.any` rather than a
sequential loop.

### P3 — Scrubber drag repaints every region on every pointermove, even when the date has not changed

### P4 — Map attribution re-serialises the style on every `sourcedata`

### C1 — The service worker caches authenticated page HTML with no principal guard **[BUG]**

`_classifySync` returns `'navigate'` for every same-origin navigation
(`static/js/sw.js:878-880`) — there is no path allowlist, denylist or auth check
anywhere in the fetch listener (`sw.js:1485-1516`). `_networkFirst` then writes
the response into shell cache storage:

```js
const response = await fetch(request);
if (response && response.ok && response.type === 'basic') {
  cache.put(request, response.clone()).catch(() => {});
}
```

(`sw.js:1423-1425`.) `/account/` renders `{{ request.user.email }}`
(`apps/accounts/templates/accounts/manage.html:206`) and the user's passkey list
(`:229`). `sign_out` (`apps/accounts/views.py:1576-1588`) calls `logout()` and
redirects — nothing purges the shell cache and nothing messages the worker.
`clearShellCachesAndReload` (`static/js/sw_register.js:494`) has only two
callers, both on the kill-switch path (`:578`, `:584`).
`templates/admin/base_site.html:35` registers the same worker on Django admin
pages, so admin HTML lands in the same bucket.

`Cache-Control: no-store` does not prevent this — Cache Storage is not the HTTP
cache and `cache.put` ignores it. `Vary: Cookie` does not either: `Cookie` is a
forbidden header name, so it is invisible to the Cache API's Vary comparison and
the match succeeds regardless of who is signed in.

The read is on the offline path only (`sw.js:1428`, inside the `catch`), so the
trigger is narrow but real: user A visits `/account/` and signs out, the device
goes offline, and the next navigation to `/account/` is served A's rendered
page, email address included. This is the one persistent store in the PWA with
no principal partitioning — the mutation queue has the SNOW-462 reconcile
(`sw.js:1754-1781`), the overlay cache has SNOW-493
(`map_overlay_offline_cache.js:47`, `:128-133`), the shell HTML cache has
nothing. Neither `docs/offline-first.md` nor `docs/offline-map.md` addresses
caching authenticated navigations, so this is unstated rather than accepted.

Skip `cache.put` for a response carrying `Cache-Control: no-store` (or add a
same-origin path denylist covering `/account/`, `/admin/`, `/sign-in/`), and
stamp the cached navigation with the current principal so the offline read can
reject a mismatch. Cover it: sign in, visit `/account/`, sign out, go offline,
navigate back, assert the email is not rendered.

### C2 — The offline banner is revealed by any fetch rejection and has no path back to hidden **[BUG]**

The reveal is driven by "a request failed"; the hide only by "the browser fired
`online`". `renderBanner(true)` has exactly two callers — the `online` listener
(`static/js/pwa_offline.js:436-440`) and `init()` (`:487`). Nothing else can
re-hide it. The wrapper at `pwa_offline.js:381-386` catches every rejection,
including `AbortError`.

A routinely-hit trigger sits on the sign-in page.
`apps/accounts/templates/accounts/sign_in.html:194-196` starts the WebAuthn

`sign_in.html:170-175` (password toggle) hits the same abort.

A fully-online user typing their email address gets a persistent "Offline — last
synced —" bar pinned above the nav for the life of the page. The banner is
in-flow, not fixed (`templates/includes/_offline_banner.html:25-28`), so it
