01

The one idea you need before reading any of the code

A web map is not a picture, and nothing in this codebase draws anything.

The library doing the drawing is MapLibre. Think of it as a small rendering engine with a declarative interface, closer to a scene graph than to a canvas API. You never issue a draw call. You hand it two things:

Sources — where data comes from. A source is a URL plus a format: "fetch this GeoJSON", "fetch these image tiles". Layers — how to paint a source. A layer names its source, picks a shape (fill, line, symbol, raster), and gives paint rules for colour, width and opacity. MapLibre resolves that description into WebGL every frame.

Everything in map.js is therefore one of four verbs: add a source, add a layer, change a property on a layer, or attach state to a feature. There is no render loop of ours anywhere. When the map changes, it is because one of those four things changed and MapLibre redrew.

The second thing worth internalising: paint rules are not functions, they are data. A colour is written as a small JSON expression the engine evaluates per feature — a lookup table, not a callback. That is why colouring 149 polygons costs nothing: we are not calling our code 149 times, we are handing the GPU a table.

Why this matters for reading the code

If you go looking for the function that draws a region, you will not find it. Look instead for the function that describes the region layer — installRegionsLayers — and for the function that changes one number on it later.

02

What is actually on screen

Three independent stacks, from three different owners, composited by z-order.

The map looks like one image. It is three stacks that know nothing about each other, and almost every subtlety in the code comes from that separation.

The consequence people trip over: the basemap is not a background image, it is a whole style document. Switching from OpenFreeMap to swisstopo replaces the entire scene — our sources and layers included. Everything we added has to be re-added, and everything we coloured has to be re-coloured. repaintAfterStyleSwap exists for exactly that, and it is 215 lines.

03

The trick that makes the season scrubber instant

Separate the shape of a thing from what is currently true about it.

Dragging the scrubber recolours all 149 regions for a different day. Naïvely, that is a request per day and a re-upload of every polygon. It is neither.

MapLibre lets you attach a small bag of values to a feature beside the geometry, without touching the source — feature-state. The fill layer's colour expression reads that bag. So the geometry is uploaded to the GPU exactly once, and changing a day is 149 assignments into a side table.

This is a genuinely good decision and it pays for itself twice: it is why the scrubber feels native, and it is why the whole season fits in 40 KB.

It has one sharp edge, and the codebase has been cut by it. Feature-state lives with the source. Destroy the source — which is what a basemap swap does — and every region falls back to "no rating" and the map goes grey. So every style change must trigger a full repaint from whatever day is currently displayed. That is a real coupling between two features that otherwise have nothing to do with each other, and it is the reason a basemap picker is 500 lines rather than 50.

The compensating design

Danger colours are painted opaque, with transparency pre-blended into the colour by choropleth_core.js. A translucent fill would blend with whatever basemap is underneath, so the same rating rendered as five different colours across five basemaps. On a safety product that is not a cosmetic bug.

04

Where the code lives, and the one rule that governs it

75 first-party files, no bundler, no import statements. Load order is the dependency graph.

Browsers offer two ways to load a script. Modules declare their dependencies with import and each gets a private namespace. Classic scripts — the older form — all share one namespace, and a name declared in one file is visible in every file that loads after it.

Snowdesk uses classic scripts throughout. In practice these 75 files behave like a single file that happens to be split across 75 tabs: a variable declared in map_state.js is simply in scope by the time map.js runs. There is no import graph to read. The graph is the order of <script> tags in the template.

For a reader coming from a language with real modules, the closest analogue is a C build with no headers, where the compiler concatenates translation units in the order given and every symbol is global. The consequence is the same: correctness depends on order, and order is not checked by the language.

Two things stop this being reckless. The template's order and the test harness's order are asserted against each other by a Python test, so adding a file in one place and forgetting the other is a red build rather than a map that silently stops booting. And a second linter, js-globals-lint, fails on any read of a global name that nothing anywhere assigns.

That second linter exists because of a real bug, and it is worth knowing as a cautionary tale. One module read window.MAP for its entire life. map.js declares a bare let MAP — which lands in the shared scope but not on the window object. So the read returned "undefined" every time, forever, and every guard around it silently took the "no map yet" branch. Nothing threw. Nothing logged. The feature just never worked.

Files outside the bundle

Modules loaded from their own partials can't rely on being after map.js, so they reach shared state through an explicitly published object, window.snowdeskMapState. It is frozen, so a typo throws instead of returning undefined. Knowing which of the two routes a file is allowed to use is the single most load-bearing piece of tribal knowledge in this codebase.

05

How 75 files that can't call each other manage to co-operate

A message bus, and a rule that each fact has exactly one writer.

Without imports there is no clean way for the calendar to call into the scrubber. So the files broadcast instead. The browser's own event system is used as a publish/subscribe bus: anyone can fire a named message at the document, anyone can listen for it, and neither side needs a reference to the other.

The important discipline layered on top is one writer per fact. "Which day is shown" is the fact most things depend on. Three surfaces can change it — the scrubber, the calendar, the timelapse — but only one function commits it. The calendar does not write the URL or repaint anything; it fires snowdesk:scrub-to, and the scrubber's commitDate does the work. Everything downstream then hears one message, snowdesk:date-changed.

That is the right call, and the reason is stated plainly in the docs: two surfaces writing the URL is two places for the URL and the painted map to drift apart.

The same pattern solves a second problem. Twelve surfaces float over the map — panels, menus, popups, a help tour — and only one is ever meaningful at once. Rather than each one knowing about the other eleven, every surface registers a name plus "are you open?" and "close yourself" with a small registry, and calls "I'm opening" before it appears. The registry closes the rest.

This replaced pairwise wiring that covered three of the fifteen possible relationships between six surfaces — each remembered by whichever ticket added the newest one. A test now runs the whole matrix, so a surface that forgets to register fails there rather than in production.

The honest downside

A message bus makes call sites unfindable. You cannot ask your editor "who calls this?" — you have to grep for a string. The codebase compensates with unusually thorough comments, which is a real cost paid to buy a real benefit; see finding 07.

06

The server side is deliberately boring

Plain Django views returning JSON. No REST framework, no serialisers, no GIS extension.

Every endpoint the map talks to is a function that takes a request and returns a JsonResponse. Region boundaries are stored as JSON columns rather than in PostGIS, and the one geometric operation the request path needs — "which region contains this point?" — is forty lines of ray-casting in pure Python.

Measured against this checkout, the page itself renders in 8 ms on 4 queries. That is not a rounding error in a bigger number; the server genuinely is not the interesting part, which is the correct outcome.

Two details in that table are worth stealing. The ratings payload encodes danger as a single integer per region — {"2026-02-16": {"CH-4115": 3}} — which is why a seven-month season is 40 KB rather than a megabyte of repeated strings. And the bulletin-boundary endpoint varies its cache header by date: a day old enough that no provider will revise it is served immutable for a week, which is also the signal the offline service worker uses to decide the response is worth keeping.

The bulletin-boundary endpoint used to return the whole season in one response. Once the historical archive landed, serialising every day's dissolved geometry at once pushed the web worker past its 512 MB memory limit. It now serves one day, and the client memoises per date. Worth naming out loud: the failure mode of "just send everything" scales with your archive, so it arrives long after the design decision.

07

Testing, and the rule that keeps it affordable

Three layers, and putting a test in the wrong one is treated as a defect.

The project's stated rule is to work top-down and stop at the first layer that can hold the assertion. Anything reachable from Django's test client is a Python test. Anything a browser-side module does that a simulated DOM can observe is a JavaScript unit test. Only what genuinely needs a real browser — WebGL, the service worker, real clipboard and passkey ceremonies — is an end-to-end test.

The third layer is capped at roughly a dozen tests, and the cap is enforced by a linter that also fails any test over 40 lines or any test file that doesn't name a real manual scenario. That is unusual, and it exists because the line was breached twice: a deliberate cut to 110 browser tests was back up to 280 within sixteen days, because every UI ticket dutifully bundled one and nothing said stop.

The middle layer is where the real coverage is: 157 files, 52,704 lines. To make it possible at all, a harness reads the map's files off disk and evaluates them together in one function scope — because the standard import machinery would give each file a private namespace, and every cross-file reference the browser resolves happily would become an error.

Read this as a design signal

Needing a bespoke harness to reproduce your own loading model is the clearest evidence of what the no-modules choice costs. It works, it is well documented, and it is the kind of thing that is cheap to keep and expensive to acquire — but it is a permanent tax on every new test file.

08

Review — what holds up

The parts a sceptical reader should be told about before the criticism.

  • ✓

    The server is genuinely fast. 4 queries and 8 ms for the heaviest page on the site, with a monitored query-count budget to stop that drifting.

  • ✓

    The payload is already handled. 2.9 MB of source becomes 343 KB gzipped on the wire, because the deploy minifies first-party JS in place before hashing. Two-thirds of what remains is MapLibre itself. If someone raises "you ship unminified JavaScript", they are reading the repository, not production.

  • ✓

    Client-side security posture is clean. One assignment of raw HTML in 8,274 lines, into an attribution string that is server-controlled, with the reasoning written next to it. User-supplied names go in as text everywhere.

  • ✓

    Extracting pure logic works and is already a habit. Thirteen *_core.js modules hold the maths — the choropleth palette, the calendar grid, tile arithmetic, elevation profiles — and each is unit-tested without a map at all.

  • ✓

    Three custom linters, each encoding a real production bug. Design-token drift, unassigned globals, and untranslated strings in JavaScript. Each was written after the bug it prevents, which is the right time to write one.

  • ✓

    Boot failure is compartmentalised. The three startup fetches run in parallel and each carries its own error handling, so one dead endpoint degrades one feature rather than taking the map down. That came from an incident, and the comment says so.

A map that fails to start fails silently, and nobody finds out

SNOW-893 · SNOW-894Ready for dev · Todo

static/js/map.js:718 · no global error handler anywhere in static/js

The map is constructed with no guard. If the browser can't give MapLibre a WebGL context — an old Android device, a GPU blocklist, a hardened privacy configuration — the constructor throws, and because everything in map.js lives inside one immediately-invoked function, every statement after line 718 never runs. That includes the error handler and the offline fallback style, which are both defined below it.

The other 76 scripts still load, so the page renders the full furniture — roundels, scrubber, legend, search — around an empty grey box, with no message. And a grep of the whole of static/js finds no window.onerror and no unhandled-rejection listener, so the exception is never reported. For a product whose page is safety information, "blank and silent" is the worst available failure.

Suggested fixWrap the constructor in a try/catch and render the "map unavailable" state the offline fallback already has copy for. Separately, hook window.onerror and unhandledrejection into the first-party telemetry pipeline that already exists — the queue, the beacon and the server receiver are all built; nothing is feeding them errors. Roughly fifteen lines for both.
3struct

map.js is still 8,274 lines inside a single closure

SNOW-898Ready for dev

static/js/map.js · ~150 nested functions over shared mutable state

The split from 9,192 lines to thirteen files was real work and it followed seams the file already had. But it moved siblings out; it did not reduce the core. Everything in map.js is one function scope, so nothing inside it can be reached, stubbed or tested individually — only through the whole-bundle harness with a fake map attached.

The largest single functions are installRegionsLayers (318 lines), repaintAfterStyleSwap (215), refreshDownloadedOverlay (195) and ensureCountryLoaded (177). Roughly 40% of each is comment, so they are less bad than they look — but they each mix pure decision-making with MapLibre calls, and the pure half is the half worth testing.

Suggested fixNo rewrite. Keep doing what the codebase already does well: pull the decision out into a *_core.js module that takes plain values and returns plain values, leave the MapLibre calls behind. repaintAfterStyleSwap is the best next candidate — "which day should I repaint, given a committed date, a URL parameter and a fallback" is pure logic guarding the single most fragile interaction in the app.
3struct

44,506 lines of JavaScript with no type checking and no general linter

SNOW-899Ready for dev

no eslint / tsconfig / jsconfig in the repository

The Python side has a formatter, a linter and a type checker enforced on every commit. The browser side has three custom scripts, each targeting one specific historical bug class, and nothing general at all.

This is more pointed than it sounds, because of what the custom linters are for. js-globals-lint exists to catch reads of a global name that nothing assigns — which is a misspelled or wrongly-scoped identifier, and precisely what a type checker catches for free, along with the whole family of typos, wrong argument counts and misspelled properties around it. The team wrote a bespoke tool to catch one symptom of a class of bug they have no general defence against.

Suggested fixtsc --checkJs --noEmit over static/js, opted in file by file, with types expressed as JSDoc comments so no source syntax changes and no build step is added. Start with the thirteen *_core.js modules — they are pure and small, so they will be clean almost immediately, and they are the files most likely to be reused.

2cost

The only map endpoint without a server-side cache is the biggest one

SNOW-896Ready for dev

apps/public/api.py:660 · regions_geojson

Its siblings — ratings, bulletin groupings, weather — all wrap their payload in a cache lookup keyed on country and date. regions_geojson does not: it queries, walks 149 rows and serialises every polygon on each request. Measured here at 184 KB in 121 ms, and it sits on the boot critical path in parallel with the ratings fetch.

It is mitigated, not solved. The response carries a 24-hour public cache header, so a returning browser doesn't re-ask. But the data is fixture-backed and changes only when someone imports a fixture, which makes it the best caching candidate on the site, not the one to skip. Every cold visitor and every cache-cleared reload pays the full cost, and there is no CDN in front to absorb it.

Suggested fixOne cache.get_or_set keyed on country, with the same shape the sibling endpoints already use. Two lines, and it makes the family consistent — which matters more than the milliseconds, because the inconsistency is what makes a reader wonder whether the omission was reasoned.
2cost

Two tables with the same name and shape that are not copies of each other

SNOW-897Ready for dev

map.js:4231 OVERLAY_LAYER_IDS_MAIN · map_basemap_picker.js:199 OVERLAY_LAYER_IDS

Both map an overlay name to the list of map layers it controls. Neither is a subset of the other: ten layer ids appear only in the first, five only in the second. They are a partition — one file owns some overlays, the other owns the rest — but the naming and the identical structure say "duplicate", so the first instinct on reading either is to check whether they have drifted apart.

Working out that they haven't takes reading about sixty lines of comment across two files explaining which overlays moved where and why. That analysis has to be redone by every reader, and the answer is not obvious from either site.

Suggested fixOne table in a shared file, each entry tagged with its owner, and each file filtering to what it owns. Then the partition is a property of the data rather than a fact preserved in prose, and a new overlay assigned to nobody is visible immediately. Failing that, rename both to say what they own.
1cosm

58% of the browser code is comments, and much of it is history

not ticketedwatching

25,855 comment lines against 16,424 code lines, measured across the 75 first-party files

The comments are good. They explain why, they cite ticket numbers, they warn about traps, and several of them are the only record of a hard-won lesson. This finding is not "write fewer comments".

It is that a large share of them narrate superseded behaviour. Passages read as "SNOW-660 removed this default; SNOW-793 put it back; it must never be swapped for the derived date again." To learn what the code does today, a reader has to read what it did in three previous versions and work out which sentence is current. The docs/decisions/ directory exists for exactly that history and already holds much of it, and there is a 797-line document restating a lot of the same material — so it is being maintained in three places at once, which is how the stale sentence in finding 04 survived.

Suggested fixOpportunistically, not as a project. When you touch a comment block, keep the sentence that says why the code is this way and the sentence that says what will break if you change it; move the "it used to be X, then Y" narrative into the decision record, where it is already partly written down. Zero effect on production — the deploy strips comments anyway — but a real effect on how long it takes to read a function.
10

If only three things get done

Ordered by what they buy, not by how hard they are. The stale documentation line that was second on this list is already fixed in this cycle's PR.

  1. Make failure visible (SNOW-893, SNOW-894)

    Guard the map constructor, and wire window.onerror into the telemetry pipeline that is already built and already running. An afternoon. It converts the one failure mode nobody can currently see into one that reports itself, and it will almost certainly surface things nobody has thought to look for.

  2. Cache regions.geojson (SNOW-896)

    Two lines, XS, and it closes the one place where the map's API family is inconsistent with itself. The milliseconds are secondary — an endpoint that skips the pattern its three siblings follow is what makes a reader wonder whether the omission was reasoned.

  3. Type-check the thirteen core modules (SNOW-899)

    tsc --checkJs --noEmit with JSDoc types, on the pure files only, added to the existing lint matrix. A day or two. It is the general defence the JavaScript side has never had, and it starts where the return is immediate and the friction is lowest.

Two findings were not ticketed, on purpose.

Finding 05 — the stale region_summary line in docs/map-and-api.md — was inline-fixed in this cycle's own PR. It meets the trivial-fix rule this project already applies to code reviews: single file, no behaviour change, no new tests, no new abstraction. Ticketing a one-sentence correction and then leaving it wrong for a sprint is worse than fixing it in the pass that found it.

Finding 08 — the 58% comment ratio — is recorded as watching. Its own recommendation is that it be done opportunistically, when someone is already editing a comment block. A ticket would turn that into the project the recommendation argues against, and would then sit open indefinitely because nobody schedules a prose-pruning sprint. Next cycle re-measures the ratio; if it climbs, that is a signal worth a ticket.
