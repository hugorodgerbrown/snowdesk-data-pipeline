01

The one idea you need before reading any of the code

A web map is not a picture, and nothing in this codebase draws anything.

The library doing the drawing is MapLibre. Think of it as a small rendering engine with a declarative interface, closer to a scene graph than to a canvas API. You never issue a draw call. You hand it two things:

Sources — where data comes from. A source is a URL plus a format: "fetch this GeoJSON", "fetch these image tiles". Layers — how to paint a source. A layer names its source, picks a shape (fill, line, symbol, raster), and gives paint rules for colour, width and opacity. MapLibre resolves that description into WebGL every frame.

Everything in map.js is therefore one of four verbs: add a source, add a layer, change a property on a layer, or attach state to a feature. There is no render loop of ours anywhere. When the map changes, it is because one of those four things changed and MapLibre redrew.

The second thing worth internalising: paint rules are not functions, they are data. A colour is written as a small JSON expression the engine evaluates per feature — a lookup table, not a callback. That is why colouring 149 polygons costs nothing: we are not calling our code 149 times, we are handing the GPU a table.

Why this matters for reading the code

If you go looking for the function that draws a region, you will not find it. Look instead for the function that describes the region layer — installRegionsLayers — and for the function that changes one number on it later.

02

What is actually on screen

Three independent stacks, from three different owners, composited by z-order.

The map looks like one image. It is three stacks that know nothing about each other, and almost every subtlety in the code comes from that separation.

The consequence people trip over: the basemap is not a background image, it is a whole style document. Switching from OpenFreeMap to swisstopo replaces the entire scene — our sources and layers included. Everything we added has to be re-added, and everything we coloured has to be re-coloured. repaintAfterStyleSwap exists for exactly that.

New this cycle: the slope layer stopped being swisstopo's raster, and the terrain filter stopped being its own sheet

SNOW-1073 repaints the map's slope-shading layer from the same on-device terrain-class tiles the terrain filter already drew from (docs/decisions/slope-layer-is-painted-from-our-class-tiles.md, new this cycle), rather than swisstopo's hangneigung-ueber_30 raster. slope_overlay_core.js — the raster layer's core, clean at every prior cycle — is deleted outright; slope_classes_core.js (new, @ts-check'd, tested) takes its place, shared with route_slope_core.js's route-line colouring and the terrain filter's new "colour by slope" mode. grep for SLOPE_TILE_URL and hangneigung finds only the historical comments recording the removal, nothing live. SNOW-1104 then folded the terrain filter's own standalone sheet into the standard docked map panel — one fewer bespoke chrome shape, the same MapSheet.attach registration as before. Separately, SNOW-1077 added a public −/+ zoom control (new: map_zoom_control.js/zoom_control_core.js) whose flyout names every zoom-gated feature on the page — region selection, the terrain filter, route slope colouring — against the scale, reading them from a new frozen registry, window.pwaZoomGates (map.js), that a future gated feature joins with one line and one string. See §05 for the mobile-sheet arc this registry's sibling, window.pwaMapOverlays, now covers.

03

The trick that makes the season scrubber instant

Separate the shape of a thing from what is currently true about it.

Dragging the scrubber recolours all 149 regions for a different day. Naïvely, that is a request per day and a re-upload of every polygon. It is neither.

MapLibre lets you attach a small bag of values to a feature beside the geometry, without touching the source — feature-state. The fill layer's colour expression reads that bag. So the geometry is uploaded to the GPU exactly once, and changing a day is 149 assignments into a side table.

This is a genuinely good decision and it pays for itself twice: it is why the scrubber feels native, and it is why the whole season fits in a few tens of kilobytes.

It has one sharp edge, and the codebase has been cut by it. Feature-state lives with the source. Destroy the source — which is what a basemap swap does — and every region falls back to "no rating" and the map goes grey. So every style change must trigger a full repaint from whatever day is currently displayed. That is a real coupling between two features that otherwise have nothing to do with each other, and it is the reason a basemap picker is 500 lines rather than 50.

The compensating design

Danger colours are painted opaque, with transparency pre-blended into the colour by choropleth_core.js. A translucent fill would blend with whatever basemap is underneath, so the same rating rendered as five different colours across five basemaps. On a safety product that is not a cosmetic bug. route_slope_core.js's slope-band colouring follows the same opaque-blend rule — it no longer drives the main map's route line (retired at cycle 05), but the trip page and the elevation profile still read it directly. This cycle's slope_classes_core.js (new, see §02) extracted the same five-degree palette into its own module, read by both remaining consumers — terrain_filter_core.js, whose "colour by slope" mode is now also what paints the main map's own slope layer (SNOW-1073), and route_slope_core.js — so the one ramp has one definition rather than two.

04

Where the code lives, and the one rule that governs it

96 first-party files, no bundler, no import statements. Load order is the dependency graph.

Browsers offer two ways to load a script. Modules declare their dependencies with import and each gets a private namespace. Classic scripts — the older form — all share one namespace, and a name declared in one file is visible in every file that loads after it.

Snowdesk uses classic scripts throughout. In practice these 96 files behave like a single file that happens to be split across 96 tabs: a variable declared in map_state.js is simply in scope by the time map.js runs. There is no import graph to read. The graph is the order of <script> tags in the template.

For a reader coming from a language with real modules, the closest analogue is a C build with no headers, where the compiler concatenates translation units in the order given and every symbol is global. The consequence is the same: correctness depends on order, and order is not checked by the language.

Two things stop this being reckless. The template's order and the test harness's order are asserted against each other by a Python test, so adding a file in one place and forgetting the other is a red build rather than a map that silently stops booting. And a second linter, js-globals-lint, fails on any read of a global name that nothing anywhere assigns.

That second linter exists because of a real bug, and it is worth knowing as a cautionary tale. One module read window.MAP for its entire life. map.js declares a bare let MAP — which lands in the shared scope but not on the window object. So the read returned "undefined" every time, forever, and every guard around it silently took the "no map yet" branch. Nothing threw. Nothing logged. The feature just never worked.

Files outside the bundle

Modules loaded from their own partials can't rely on being after map.js, so they reach shared state through an explicitly published object, window.snowdeskMapState. It is frozen, so a typo throws instead of returning undefined. Knowing which of the two routes a file is allowed to use is the single most load-bearing piece of tribal knowledge in this codebase. Cycle 04's seven new route_rail*/route_cursor*/route_leader*/bank_ribbon_core.js files followed that split correctly — pure state readers reach the map through window.snowdeskMapState, and the one place they deliberately diverge from an established pattern is not this one; see §09.

05

How 96 files that can't call each other manage to co-operate

A message bus, and a rule that each fact has exactly one writer.

Without imports there is no clean way for the calendar to call into the scrubber. So the files broadcast instead. The browser's own event system is used as a publish/subscribe bus: anyone can fire a named message at the document, anyone can listen for it, and neither side needs a reference to the other.

The important discipline layered on top is one writer per fact. "Which day is shown" is the fact most things depend on. Three surfaces can change it — the scrubber, the calendar, the timelapse — but only one function commits it. The calendar does not write the URL or repaint anything; it fires snowdesk:scrub-to, and the scrubber's commitDate does the work. Everything downstream then hears one message, snowdesk:date-changed.

That is the right call, and the reason is stated plainly in the docs: two surfaces writing the URL is two places for the URL and the painted map to drift apart.

MessageFired byWho reacts

The same pattern solves a second problem. Twelve surfaces float over the map — panels, menus, popups, a help tour — and only one is ever meaningful at once. Rather than each one knowing about the other eleven, every surface registers a name plus "are you open?" and "close yourself" with a small registry, window.pwaMapOverlays, and calls "I'm opening" before it appears. The registry closes the rest.

This replaced pairwise wiring that covered three of the fifteen possible relationships between six surfaces — each remembered by whichever ticket added the newest one. A test now runs the whole matrix, so a surface that forgets to register fails there rather than in production.

Four new sheets joined the registry the ordinary way; the rail joined the sheet machinery and kept its exception anyway

This cycle's mobile-sheet rollout (SNOW-1097–1101) gave the region, place, route and weather surfaces a phone sheet with peek/half/full detents. Three of the four call window.MapSheet.attach(el, …) — map_region_sheet.js:67, map_place_sheet.js:55, map_weather_detail.js:55 — which is what registers a sheet with window.pwaMapOverlays as well as binding its detents. The route rail got its own phone sheet too (SNOW-1099), but reached for window.MapSheet.bindDetents(rail, …) directly (route_rail.js:641) — the lower-level call attach itself uses, which binds the drag behaviour but does none of attach's registration. route_rail.js:18-19 still carries the same reasoning cycle 04 and 05 quoted: registering "would close it the moment any other overlay announced itself." So the rail is now a phone sheet that behaves, in every other respect, like the three that correctly exclude it from the registry — and the one place that invariant still doesn't hold gained a second, independent reason nobody has revisited it. See §09.

The honest downside

A message bus makes call sites unfindable. You cannot ask your editor "who calls this?" — you have to grep for a string. The codebase compensates with unusually thorough comments, which is a real cost paid to buy a real benefit; comments are 60.3% of the browser code this cycle (see §07 and §09) — down from 61.0% last cycle, still oscillating rather than settling.

06

The server side is deliberately boring

Plain Django views returning JSON. No REST framework, no serialisers, no GIS extension.

Every endpoint the map talks to is a function that takes a request and returns a JsonResponse. Region boundaries are stored as JSON columns rather than in PostGIS, and the one geometric operation the request path needs — "which region contains this point?" — is forty lines of ray-casting in pure Python.

Measured against this checkout on a warm cache, the page itself renders in 6 queries — unchanged for a sixth straight cycle — in roughly 35 ms (four warm runs spanned 34.6–36.5 ms on this shared sandbox; same query count as every prior cycle, so the drop from last cycle's ~50 ms reads as the same machine noise this series has flagged every cycle since 02, not a genuine speed-up).

apps/public/api.py changed this cycle, but not in the regions/ratings/resorts/groupings/weather/area-content table below: SNOW-1105 reworked weather_detail (the symbol-tap sheet's endpoint, not in this table since it is per-location rather than a page-wide feed) to read a forward day from today's row's forecast column instead of looking up a row that will not exist until that day arrives, and to render the day's hourly chart for the sheet's new FULL detent. The sheet rollout (SNOW-1098, SNOW-1100) added three new HTMX partial endpoints — api:region_sheet_partial, api:resort_sheet_partial, api:favourite_sheet_partial — each @require_htmx-guarded like its siblings and, like region_summary next to it in the table below, carrying no server-side cache of its own: a per-region or per-place fragment on a small query count, matching the existing pattern for that class of endpoint rather than a gap against it.

07

Testing, and the rule that keeps it affordable

Three layers, and putting a test in the wrong one is treated as a defect.

The project's stated rule is to work top-down and stop at the first layer that can hold the assertion. Anything reachable from Django's test client is a Python test. Anything a browser-side module does that a simulated DOM can observe is a JavaScript unit test. Only what genuinely needs a real browser — WebGL, the service worker, real clipboard and passkey ceremonies — is an end-to-end test.

The third layer is still capped at roughly a dozen tests (12 files today, unchanged for a fifth cycle; e2e-lint counts 13 test functions inside them against its backstop of 25) and the cap is still enforced by e2e-lint. The middle layer grew again: 215 files, 78,094 lines — up from 207/75,231 at cycle 05, the largest jump since cycle 04's, consistent with four new sheets, a new zoom control and a new slope-classes module each shipping its own Vitest coverage. Each of this cycle's three new *_core.js modules kept the discipline: pure, @ts-check'd, each with a dedicated tests/js/test_*.js file.

Read this as a design signal

Needing a bespoke harness to reproduce your own loading model is the clearest evidence of what the no-modules choice costs. It works, it is well documented, and it is the kind of thing that is cheap to keep and expensive to acquire — but it is a permanent tax on every new test file.
