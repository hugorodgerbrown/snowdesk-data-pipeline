01

The one idea you need before reading any of the code

A web map is not a picture, and nothing in this codebase draws anything.

The library doing the drawing is MapLibre. Think of it as a small rendering engine with a declarative interface, closer to a scene graph than to a canvas API. You never issue a draw call. You hand it two things:

Sources — where data comes from. A source is a URL plus a format: "fetch this GeoJSON", "fetch these image tiles". Layers — how to paint a source. A layer names its source, picks a shape (fill, line, symbol, raster), and gives paint rules for colour, width and opacity. MapLibre resolves that description into WebGL every frame.

Everything in map.js is therefore one of four verbs: add a source, add a layer, change a property on a layer, or attach state to a feature. There is no render loop of ours anywhere. When the map changes, it is because one of those four things changed and MapLibre redrew.

The second thing worth internalising: paint rules are not functions, they are data. A colour is written as a small JSON expression the engine evaluates per feature — a lookup table, not a callback. That is why colouring 149 polygons costs nothing: we are not calling our code 149 times, we are handing the GPU a table.

Why this matters for reading the code

If you go looking for the function that draws a region, you will not find it. Look instead for the function that describes the region layer — installRegionsLayers — and for the function that changes one number on it later.

02

What is actually on screen

Three independent stacks, from three different owners, composited by z-order.

The map looks like one image. It is three stacks that know nothing about each other, and almost every subtlety in the code comes from that separation.

The consequence people trip over: the basemap is not a background image, it is a whole style document. Switching from OpenFreeMap to swisstopo replaces the entire scene — our sources and layers included. Everything we added has to be re-added, and everything we coloured has to be re-coloured. repaintAfterStyleSwap exists for exactly that.

Established at cycle 07: a trip's route shares its drawing code with the main map, the Plan page and the meeting picker

SNOW-1212 extracted the route-drawing logic into route_drawing_core.js; the main map's own call (installTripRouteLayers) is idempotent, calls raiseMarkerLayers(), and re-runs from repaintAfterStyleSwap like every install function on the page. This cycle's SAC-tours work is the second consumer to join since — see below.

New this cycle: SAC's ski tours are drawn on the main map too, outside repaintAfterStyleSwap's own block

"Find a route" (SNOW-1276–1310) draws SAC's ski tours as a third consumer of route_drawing_core.js's shared install — a halo, legs and a cursor, exactly as a route or a trip is drawn. It is idempotent on its source and inserts every layer with before: 'regions-line', so it never needs its own raiseMarkerLayers() call — markers raised by every other install function stay above it by construction, since inserting before a layer never reorders ones already raised. What is new: it does not go through the central repaintAfterStyleSwap reinstall block at all. It owns its own map.on('styledata', …) listener (ski_tours.js:677) that re-runs its own install on every style change — the only other precedent for this is the staff-only map_edit_resorts.js. The listener is safe unthrottled because the function it calls is itself fully guarded (zoom-mode early-outs, a covers-the-viewport memo); the one listener that fires on every pan and zoom gesture, moveend, is correctly debounced. The whole feature sits behind the route_drawing flag (see the figure caption above), so none of this runs for an ordinary visitor today — but the pattern it establishes, a second valid way for a layer to survive a basemap swap, is worth knowing before a third feature invents a third one.

03

The trick that makes the season scrubber instant

Separate the shape of a thing from what is currently true about it.

Dragging the scrubber recolours all 149 regions for a different day. Naïvely, that is a request per day and a re-upload of every polygon. It is neither.

MapLibre lets you attach a small bag of values to a feature beside the geometry, without touching the source — feature-state. The fill layer's colour expression reads that bag. So the geometry is uploaded to the GPU exactly once, and changing a day is 149 assignments into a side table.

This is a genuinely good decision and it pays for itself twice: it is why the scrubber feels native, and it is why the whole season fits in a few tens of kilobytes.

It has one sharp edge, and the codebase has been cut by it. Feature-state lives with the source. Destroy the source — which is what a basemap swap does — and every region falls back to "no rating" and the map goes grey. So every style change must trigger a full repaint from whatever day is currently displayed. That is a real coupling between two features that otherwise have nothing to do with each other, and it is the reason a basemap picker is 500 lines rather than 50.

The compensating design

Danger colours are painted opaque, with transparency pre-blended into the colour by choropleth_core.js. A translucent fill would blend with whatever basemap is underneath, so the same rating rendered as five different colours across five basemaps. On a safety product that is not a cosmetic bug. slope_classes_core.js's five-degree palette, shared since cycle 06 by the main map's slope layer, the route line's slope colouring and the terrain filter, follows the same rule and is untouched this cycle.

04

Where the code lives, and the one rule that governs it

127 first-party files, no bundler, no import statements. Load order is the dependency graph.

Browsers offer two ways to load a script. Modules declare their dependencies with import and each gets a private namespace. Classic scripts — the older form — all share one namespace, and a name declared in one file is visible in every file that loads after it.

Snowdesk uses classic scripts throughout. In practice these 127 files behave like a single file that happens to be split across 127 tabs: a variable declared in map_state.js is simply in scope by the time map.js runs. There is no import graph to read. The graph is the order of <script> tags in the template.

For a reader coming from a language with real modules, the closest analogue is a C build with no headers, where the compiler concatenates translation units in the order given and every symbol is global. The consequence is the same: correctness depends on order, and order is not checked by the language.

Two things stop this being reckless. The template's order and the test harness's order are asserted against each other by a Python test, so adding a file in one place and forgetting the other is a red build rather than a map that silently stops booting — re-run against this cycle's own additions, still green. And a second linter, js-globals-lint, fails on any read of a global name that nothing anywhere assigns.

That second linter exists because of a real bug, and it is worth knowing as a cautionary tale. One module read window.MAP for its entire life. map.js declares a bare let MAP — which lands in the shared scope but not on the window object. So the read returned "undefined" every time, forever, and every guard around it silently took the "no map yet" branch. Nothing threw. Nothing logged. The feature just never worked.

Files outside the bundle

Modules loaded from their own partials can't rely on being after map.js, so they reach shared state through an explicitly published object, window.snowdeskMapState. It is frozen, so a typo throws instead of returning undefined. Knowing which of the two routes a file is allowed to use is the single most load-bearing piece of tribal knowledge in this codebase. This cycle's new overlay-adjacent file, map_alerts.js (the date row's bell, now listing bulletin alerts — SNOW-1333), loads inside the main bundle and reaches map.js's state directly, correctly; it did not need the window.snowdeskMapState route.

05

How 119 files that can't call each other manage to co-operate

A message bus, and a rule that each fact has exactly one writer.

Without imports there is no clean way for the calendar to call into the scrubber. So the files broadcast instead. The browser's own event system is used as a publish/subscribe bus: anyone can fire a named message at the document, anyone can listen for it, and neither side needs a reference to the other.

The important discipline layered on top is one writer per fact. "Which day is shown" is the fact most things depend on. Three surfaces can change it — the scrubber, the calendar, the timelapse — but only one function commits it. The calendar does not write the URL or repaint anything; it fires snowdesk:scrub-to, and the scrubber's commitDate does the work. Everything downstream then hears one message, snowdesk:date-changed.

That is the right call, and the reason is stated plainly in the docs: two surfaces writing the URL is two places for the URL and the painted map to drift apart.

The same pattern solves a second problem. A growing set of surfaces float over the map — panels, menus, popups, a help tour — and only one is ever meaningful at once. Rather than each one knowing about the others, every surface registers a name plus "are you open?" and "close yourself" with a small registry, window.pwaMapOverlays, and calls "I'm opening" before it appears. The registry closes the rest.

The route rail's exception is now written down — and the gap it named is fixed

SNOW-1040 is closed this cycle, two ways. First, a decision doc landed — docs/decisions/the-route-rail-keeps-its-own-lifetime.md — naming the rail's non-registration a deliberate choice: the rail is the one surface a reader studies while checking other flyouts, so the registry's "opening anything closes everything else" rule is wrong for it specifically, and it joins the narrower one-object-sheet-at-a-time rule instead. Second, the doc's own "Consequences" section named a real, then-unfixed gap — Escape closed a flyout and also cleared the route's point or closed the route, because the rail's capture-phase check carried none of the registry's signals. The same cycle fixed it (SNOW-1335): the rail's Escape check now also reads window.pwaMapOverlays.openNames(), so closing the layers menu, zoom, calendar, alerts, help or legend flyout no longer touches the route underneath. A decision that names its own open edge, in the same breath as making the exception, is the shape this series has been asking every overlay-adjacent surface for since cycle 04 — the rail took longest, but got there completely.

New this cycle: the map's bell becomes an overlay too

The date row's bell (SNOW-1333) now lists your bulletin alerts rather than being decorative. map_alerts.js answers the registry question the ordinary way — window.pwaMapOverlays.register(OVERLAY_NAME, {...}) — so opening it closes whatever else was open, and opening anything else closes it. One more surface, one more correct registration, no exception needed.

The honest downside

A message bus makes call sites unfindable. You cannot ask your editor "who calls this?" — you have to grep for a string. The codebase compensates with unusually thorough comments, which is a real cost paid to buy a real benefit; comments are 57.6% of the browser code this cycle (see §07 and §09) — down from 61.5% last cycle, a bigger single-cycle move than any before it. Code lines grew faster than comment lines this time (30,405 vs 25,333, +20%; comment lines 41,222 vs 40,458, +2%) — plausibly because several of this cycle's biggest arcs are dense state machines (the SAC-tours drawing, the offline-save plumbing) rather than the heavily-annotated onboarding surfaces that pushed the ratio up at cycles 05–07. Still nothing to act on; still watching.

06

The server side is deliberately boring

Plain Django views returning JSON. No REST framework, no serialisers, no GIS extension.

Every endpoint the map talks to is a function that takes a request and returns a JsonResponse. Region boundaries are stored as JSON columns rather than in PostGIS, and the one geometric operation the request path needs — "which region contains this point?" — is forty lines of ray-casting in pure Python.

Measured against this checkout on a warm cache, the page itself renders in 8 queries (was 7) in roughly 40–63 ms across runs. The eighth is new: resort_guide.popular_resorts() (SNOW-1231), one query for four fixed resort slugs with one join, feeding the "Find a resort" onboarding walkthrough. It runs unconditionally, uncached, on every /map/ request — the same shape as cycle 07's accepted onboarding cost (RouteShare.objects.example().exists()), a small fixed cost paid by every visitor for a feature most will use once or never, and ruled out as a finding on the same precedent: a single, described, bounded-size query, not a fan-out.

Three endpoints are genuinely new this cycle: api:ski_network_geojson, api:ski_tours_geojson and api:ski_summits_json (SNOW-1276–1294), each behind the "Find a route" draw-mode tooling and each read in full against the "boring, cacheable, no request.user" shape this table has praised since cycle 02. Two of the three hold it: ski_network_geojson and ski_summits_json are both @vary_on_headers("Accept-Encoding") only, matching every sibling in the file. The third does not — see the finding below. A fourth new endpoint, api:area_items (SNOW-965), is correctly the opposite shape: it answers the signed-in reader's own trips and pins, so it is private, no-store with a deliberate Vary: Cookie, naming its viewer in X-Snowdesk-Principal. region_sheet_partial/resort_sheet_partial/favourite_sheet_partial gained a real improvement this cycle (SNOW-1318): resort_sheet_partial dropped a per-request Favourite.objects.filter(...) query — the Save star now paints client-side from the favourites feed map.js already holds — and moved from private, no-store to a properly cacheable day/10-minute split, the exact direction this series has been asking for elsewhere.

07

Testing, and the rule that keeps it affordable

Three layers, and putting a test in the wrong one is treated as a defect.

The project's stated rule is to work top-down and stop at the first layer that can hold the assertion. Anything reachable from Django's test client is a Python test. Anything a browser-side module does that a simulated DOM can observe is a JavaScript unit test. Only what genuinely needs a real browser — WebGL, the service worker, real clipboard and passkey ceremonies — is an end-to-end test.

The third layer is still capped at roughly a dozen tests (12 files, 13 test functions, unchanged for a seventh cycle against e2e-lint's backstop of 25) and the cap is still enforced by e2e-lint. The middle layer grew again: 278 files, 101,444 lines — up from 245/89,125 at cycle 07, tracking the eight new *_core.js modules (each shipping with its own Vitest file, see §04) plus the SAC-tours and offline-hardening arcs' own test coverage, which this count does not separate out from the rest of the map's.

Read this as a design signal

Needing a bespoke harness to reproduce your own loading model is the clearest evidence of what the no-modules choice costs. It works, it is well documented, and it is the kind of thing that is cheap to keep and expensive to acquire — but it is a permanent tax on every new test file.

The new ski-tours endpoint varies on Cookie, defeating the public-cache policy it's meant to have

SNOW-1365Todo, scoped, Codex review requested

apps/public/api.py:1549 ski_tours_geojson — @vary_on_headers("Accept-Encoding", "Accept-Language", "Cookie"), _geojson_response's public=True policy

This file states a rule three times over: a publicly-cacheable GeoJSON endpoint must never carry Vary: Cookie unless it reads request.user, because Django's SessionMiddleware appends that header on its own and a bare @vary_on_headers("Accept-Encoding") is specifically what pre-empts it. major_regions_geojson's docstring says so explicitly; area_content's and weather_geojson's table entries in docs/map-and-api.md say the same thing from the other side ("nothing on the path may read request.user or Vary: Cookie would defeat it"). ski_tours_geojson reads nothing but request.GET — no request.user, no session — yet carries Cookie in its vary tuple regardless, present since the endpoint's first commit (4ff475b6). Its own documentation entry (docs/map-and-api.md:617) only ever claimed "Varies on Accept-Language" — further evidence this is an unreviewed carry-over, not a considered choice; there is no LocaleMiddleware configured, so the language vary is genuinely driven by the header, never a cookie. Effect: every signed-in visitor gets a private cache entry for data that is identical for everyone. Not user-visible and not a correctness bug — the data served is right either way — which is why this sits at severity 2 rather than higher, but it is a clear, avoidable deviation from a rule this file states three times elsewhere, on code that shipped this cycle.

CheckRead the full function body (no request.user/request.session access); read every sibling @vary_on_headers call in the file and the three endpoints that state the rule in prose; read docs/map-and-api.md:617's own entry; checked config/settings/ for a locale cookie (none); traced the decorator to its introducing commit.

Why the same discipline that closed three findings also found two new ones. Closing a carried-forward finding and finding a new one are the same act — checking a specific claim against the code rather than against a doc or a ticket. SNOW-1093's own sixteen-file list looked exhaustive because a previous grep produced it; re-running the grep one directory wider than that list, rather than trusting it, is what found SNOW-1364. SNOW-1365 came from reading one file's own stated rule — "a public endpoint must never vary on Cookie without reading request.user" — and checking every decorator against it by hand, rather than trusting that new code follows old conventions by default. This document re-ran six lint/type guards (ds-lint, js-globals-lint, i18n-lint, e2e-lint, fidelity-lint, js-types — all clean, see §08) plus docs-lint on itself, re-measured every figure in the strip from scratch, and read all 165 commits against the subsystem boundary rather than trusting any commit title.

Figures measured against this checkout on 1 November 2026 — page render and query counts via the Django test client (warm cache; DEBUG=True, connection.queries), and independently cross-checked against a scratch worktree of the previous baseline (b09d298) to isolate exactly which query was new. Wire sizes are gzip −9 over the deploy's own minified output, produced from an isolated scratch copy of static/js plus its own copy of bin/minify-js and a node_modules link, laid out as <scratch>/bin/minify-js next to <scratch>/static so path.resolve(__dirname, '..') resolves correctly — the repo's own static/js was never touched (git status --short confirmed before and after). The wire-cost figure covers all 129 scripts the map page serves (127 first-party, minified and gzipped from the scratch copy, plus the 2 vendored *.min.js bundles gzipped as shipped) — 439.0 KiB (217.1 KiB first-party, 221.9 KiB vendor), up from 419.2 KiB at cycle 07, proportional to the 8 extra first-party files. Layer/source counts are exact id-by-id resolution — literal, a same-file const, or a loop's return value counted at each of its call sites — restricted to the 127 files /map/ actually serves, cross-checked against git diff b09d298..HEAD -- static/js/map.js rather than a bare id count, which is what separated this cycle's one genuinely new layer-owning call site (the SAC tour) from a pre-existing one that gained extra layers in place (the route-cursor halo, applying at all three of its call sites, not just the new one). Function sizes are brace-matched from each declaration, not taken as a raw span to the next top-level declaration — the series' own cycle-01 mistake — and code lines are reported separately from total span; the largest function this cycle, installRegionsLayers at 181 code lines (326-line span), was sanity-checked to end cleanly before the next declaration's header comment, with no swallowing.
