01

The one idea you need before reading any of the code

A web map is not a picture, and nothing in this codebase draws anything.

The library doing the drawing is MapLibre. Think of it as a small rendering engine with a declarative interface, closer to a scene graph than to a canvas API. You never issue a draw call. You hand it two things:

Sources — where data comes from. A source is a URL plus a format: "fetch this GeoJSON", "fetch these image tiles". Layers — how to paint a source. A layer names its source, picks a shape (fill, line, symbol, raster), and gives paint rules for colour, width and opacity. MapLibre resolves that description into WebGL every frame.

Everything in map.js is therefore one of four verbs: add a source, add a layer, change a property on a layer, or attach state to a feature. There is no render loop of ours anywhere. When the map changes, it is because one of those four things changed and MapLibre redrew.

The second thing worth internalising: paint rules are not functions, they are data. A colour is written as a small JSON expression the engine evaluates per feature — a lookup table, not a callback. That is why colouring 149 polygons costs nothing: we are not calling our code 149 times, we are handing the GPU a table.

Why this matters for reading the code

If you go looking for the function that draws a region, you will not find it. Look instead for the function that describes the region layer — installRegionsLayers — and for the function that changes one number on it later.

02

What is actually on screen

Three independent stacks, from three different owners — and now one more axis: which of two modes the map is in.

The map looks like one image. It is three stacks that know nothing about each other, and almost every subtlety in the code comes from that separation.

The consequence people trip over: the basemap is not a background image, it is a whole style document. Switching from OpenFreeMap to swisstopo replaces the entire scene — our sources and layers included. Everything we added has to be re-added, and everything we coloured has to be re-coloured. repaintAfterStyleSwap exists for exactly that, and is unchanged this cycle.

New this cycle: the map now has two modes, and a layer belongs to one, the other, or both

SNOW-1394/1421/1422 (behind the map_modes flag) give the map a Dated segment ("Conditions": the bulletins, the bulletin-grouping outline, weather, the season scrubber) and a Terrain segment (steep terrain, ski tours, ski summits, rest zones) — and most of the stack (regions, routes, resorts, pins) is shared. The discipline is named explicitly in the decision doc: suppression, never preference. Switching modes never calls an overlay's own show()/hide() and never writes its stored setting — it ANDs a mode-only SUPPRESSION.MAP_MODE flag onto whatever the reader already chose, through each overlay's setSuppressed hook (pwaMapModeCore.ONLY_IN). Leaving Terrain brings every overlay back exactly as it was. See the decision doc.

3D is a view of either mode, not a mode of its own

A second 3D arc this cycle (SNOW-1438–1470-ish) replaced the standalone /map/3d/ page (now a redirect, SNOW-1450) with ?view=3d on /map/ itself. SNOW-1449 first offered it in Terrain only; SNOW-1452 (6 Nov) widened it to both modes, so the mode says what the map shows and the view says how it is drawn — in Dated the danger fill becomes a light wash and problem terrain drapes on the relief. The view is never stored and never written into the mode: a bare /map/ always opens flat. All of it — map_3d_core.js, the terrain/DEM install, the fly-past recorder, the device test panel — sits behind the map_3d flag and loads outside the map bundle when the flag is off, the same discipline cycle 08 praised for the SAC-tours prototype. A second large prototype, a second clean boundary.

And a third: the winter map past the Swiss border

map_beyond_switzerland (SNOW-1460) restyles OpenStreetMap vector tiles with the winter style's own layers, clips them to outside the swisstopo extent, and adds our own relief from DEM tiles and swisstopo's scree pattern on OSM scree — in 2D and 3D. Also flag-gated, also outside the bundle when off, also correctly inert for an ordinary visitor today.

03

The trick that makes the season scrubber instant

Separate the shape of a thing from what is currently true about it.

Dragging the scrubber recolours all 149 regions for a different day. Naïvely, that is a request per day and a re-upload of every polygon. It is neither.

MapLibre lets you attach a small bag of values to a feature beside the geometry, without touching the source — feature-state. The fill layer's colour expression reads that bag. So the geometry is uploaded to the GPU exactly once, and changing a day is 149 assignments into a side table.

This is a genuinely good decision and it pays for itself twice: it is why the scrubber feels native, and it is why the whole season fits in a few tens of kilobytes.

It has one sharp edge, and the codebase has been cut by it. Feature-state lives with the source. Destroy the source — which is what a basemap swap does — and every region falls back to "no rating" and the map goes grey. So every style change must trigger a full repaint from whatever day is currently displayed. That is a real coupling between two features that otherwise have nothing to do with each other, and it is the reason a basemap picker is 500 lines rather than 50.

The compensating design

Danger colours are painted opaque, with transparency pre-blended into the colour by choropleth_core.js. A translucent fill would blend with whatever basemap is underneath, so the same rating rendered as five different colours across five basemaps. On a safety product that is not a cosmetic bug. slope_classes_core.js's five-degree palette, shared since cycle 06 by the main map's slope layer, the route line's slope colouring and the terrain filter, follows the same rule and is untouched this cycle.

04

Where the code lives, and the one rule that governs it

146 first-party files, no bundler, no import statements — but production now ships them as two files, not 129.

Browsers offer two ways to load a script. Modules declare their dependencies with import and each gets a private namespace. Classic scripts — the older form — all share one namespace, and a name declared in one file is visible in every file that loads after it.

Snowdesk uses classic scripts throughout, and the load-order discipline from earlier cycles is completely unchanged: a variable declared in map_state.js is simply in scope by the time map.js runs, and the graph is the order of names in a list rather than the order of <script> tags in a template. What changed this cycle is where that list lives and what it becomes in production.

New this cycle: the map's scripts ship as two built bundles (SNOW-1412)

static/js/bundles/map.txt (87 members) and static/js/bundles/map_surfaces.txt (42 members) now name the load order as a plain text list, one filename per line, instead of the order of script tags in map.html. {% js_bundle "map" %} (apps/public/templatetags/js_bundles.py) renders one tag per member when settings.JS_BUNDLES is off (development, tests — so every file is still independently debuggable locally) and one tag for the built file when it is on (staging, production, perf). bin/bundle-jsbin/minify-js and before collectstatic, in bin/build.sh. The two Python and Node readers share the same tiny list-parsing format on purpose.

The reason is reliability, not bytes: each of the ~125 separate scripts was its own entry in the service worker's shell cache, so a device could hold some and not others — after a dropped carry, a part-way-failed warm, an eviction — and the map then booted with some features silently missing. One file per list is either cached or it is not. See the decision doc for the accepted trade-offs: a top-level throw in one member now stops every member after it in that bundle (accepted — wrapping members in try {} would break the shared scope); there is no source map in production (decided 2026-11-03, nothing reads one today); a member that opened with 'use strict' would be refused by bin/bundle-js rather than silently change the whole bundle's strictness.

The practical consequence: 22 script tags on production, not 148

A development or test request to /map/ still renders 148 <script> tags (146 first-party, 2 vendor) exactly as it always has. On staging and production that collapses to the two built bundles, plus the ~18 scripts that are base.html's own PWA-shell scripts rather than map bundle members (db.js, pwa_install.js, sw_register.js and the rest — unconditional on every page, not just the map), plus the 2 vendored files — 22 tags in total. Adding a map module now means adding it to the right list at the right position, not tagging it in the template — tests/public/templatetags/test_js_bundles.py checks every member exists and is listed exactly once and that each list renders as one contiguous run in order, and tests/map/test_map_script_order.py still checks the order Vitest boots against. 05

How files that can't call each other manage to co-operate

A message bus, a rule that each fact has exactly one writer — and now a second discipline built the same way: suppress, never prefer.

Without imports there is no clean way for the calendar to call into the scrubber. So the files broadcast instead. The browser's own event system is used as a publish/subscribe bus: anyone can fire a named message at the document, anyone can listen for it, and neither side needs a reference to the other.

The important discipline layered on top is one writer per fact. "Which day is shown" is the fact most things depend on. Three surfaces can change it — the scrubber, the calendar, the timelapse — but only one function commits it. Unchanged this cycle, and the table below is identical to cycle 08's.

The same overlay registry from earlier cycles is unchanged too: a growing set of surfaces float over the map, only one is ever meaningful at once, and each registers a name plus "are you open?" and "close yourself" with window.pwaMapOverlays.

The own-styledata-listener pattern is now a recognised fourth instance, not a one-off

Cycle 08 noted that the SAC-tours drawing was the second feature (after the staff-only resort editor) to own its own map.on('styledata', …) reinstall rather than go through the central repaintAfterStyleSwap block, and flagged it as "worth knowing before a third feature invents a third one." This cycle adds two more on the same shape: map_view_3d.js's terrain relief (map.on('styledata', reinstall); map.on('style.load', reinstall)) and rest_zones.js (map.on('styledata', ready)). Both are safe for the reason cycle 08's instance was: the function behind the listener is itself idempotent and cheaply guarded, so re-running it on every style event costs nothing extra. No shared helper has been written for this shape across four independent implementations; see §10.

New this cycle: suppression, never preference, as a second instance of the same discipline

The Dated/Terrain mode toggle (§02) states its own rule explicitly, in the decision doc, in words that could describe the date-write rule above without changing a noun: a mode switch is never allowed to rewrite a reader's stored choice, only to AND a temporary hold onto it. pwaMapModeCore.ONLY_IN is the per-mode table; isSuppressed(key, mode) and suppressedIn(mode) are read, never written to, by the overlays themselves; what is actually drawn is "the reader's preference AND-ed with not held" (pwaMapModeCore.effective). It is the same shape as "one writer per fact" applied to visibility instead of to a date, and it is reused correctly at both of this cycle's new boundaries — the Dated/Terrain toggle itself and, more narrowly, the one route-draw exception that is also written down: rest zones show in either mode while a route is being drawn, regardless of the switch, and the general-purpose overlay-visibility-changed backstop is told to leave that one key alone.

06

The server side is deliberately boring

Plain Django views returning JSON — now living in apps/map, not apps/public.

Every endpoint the map talks to is a function that takes a request and returns a JsonResponse. Region boundaries are stored as JSON columns rather than in PostGIS, and the one geometric operation the request path needs — "which region contains this point?" — is forty lines of ray-casting in pure Python. None of that changed; what changed is the file it all lives in: apps/map/api.py (SNOW-1428, §04), carrying forward the same docstring-as-index convention cycle 02 first described.

Measured against this checkout on a warm cache, the page itself renders in 7 queries (was 8) in roughly 45–58 ms across runs — within cycle 08's 40–63 ms range, not a regression. Two endpoints are genuinely new this cycle: api:rest_zones_geojson (SNOW-1384, the wildlife-rest-zones layer named in §02, behind route_drawing like the SAC-tours endpoints) and api:map_3d_test_receive (SNOW-1456, a rate-limited POST that stores one anonymous device-capability result from "Test 3D on this device").

A second endpoint reads the Vary-on-Cookie rule correctly, where its still-unfixed neighbour does not

rest_zones_geojson carries @vary_on_headers("Accept-Encoding", "Accept-Language", "Cookie") — the same decorator shape as the still-open SNOW-1365 finding below — but its own docstring states why: "the flag is read off the session, hence the Vary on Cookie, so a shared cache never hands one reader's answer to a reader the flag does not cover." flag_is_active(request, "route_drawing") genuinely does consult the request's session for per-user targeting, so this one is correct by inspection — the same check this series ran against ski_tours_geojson last cycle, applied to a brand-new endpoint, with the opposite verdict. 07

Testing, and the rule that keeps it affordable

Three layers, and putting a test in the wrong one is treated as a defect.

The project's stated rule is unchanged: work top-down and stop at the first layer that can hold the assertion. The third layer is still capped at roughly a dozen tests — now 13 files, 15 test functions (against e2e-lint's backstop of 25, up from 12/13 last cycle, one new journey added). The middle layer grew again: 316 files, 118,028 lines — up from 278/101,444 at cycle 08, tracking the twelve new *_core.js modules (each shipping with its own Vitest file, §04) plus coverage for the mode toggle and the 3D/relief rebuild.

Read this as a design signal

Needing a bespoke harness to reproduce your own loading model is the clearest evidence of what the no-modules choice costs. Unchanged assessment from every prior cycle.
