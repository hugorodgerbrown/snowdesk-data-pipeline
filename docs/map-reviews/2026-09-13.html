01

The one idea you need before reading any of the code

A web map is not a picture, and nothing in this codebase draws anything.

The library doing the drawing is MapLibre. Think of it as a small rendering engine with a declarative interface, closer to a scene graph than to a canvas API. You never issue a draw call. You hand it two things:

Sources — where data comes from. A source is a URL plus a format: "fetch this GeoJSON", "fetch these image tiles". Layers — how to paint a source. A layer names its source, picks a shape (fill, line, symbol, raster), and gives paint rules for colour, width and opacity. MapLibre resolves that description into WebGL every frame.

Everything in map.js is therefore one of four verbs: add a source, add a layer, change a property on a layer, or attach state to a feature. There is no render loop of ours anywhere. When the map changes, it is because one of those four things changed and MapLibre redrew.

The second thing worth internalising: paint rules are not functions, they are data. A colour is written as a small JSON expression the engine evaluates per feature — a lookup table, not a callback. That is why colouring 149 polygons costs nothing: we are not calling our code 149 times, we are handing the GPU a table.

Why this matters for reading the code

If you go looking for the function that draws a region, you will not find it. Look instead for the function that describes the region layer — installRegionsLayers — and for the function that changes one number on it later.

02

What is actually on screen

Three independent stacks, from three different owners, composited by z-order.

The map looks like one image. It is three stacks that know nothing about each other, and almost every subtlety in the code comes from that separation.

The consequence people trip over: the basemap is not a background image, it is a whole style document. Switching from OpenFreeMap to swisstopo replaces the entire scene — our sources and layers included. Everything we added has to be re-added, and everything we coloured has to be re-coloured. repaintAfterStyleSwap exists for exactly that.

Correction from cycle 01

This section previously said repaintAfterStyleSwap was 215 lines. It is 14 — the 215 was cycle 01's own measurement bug (a function's span taken as "to the next top-level declaration", which swallowed the 180-line styledata handler that follows it). The pure decision it makes was already extracted into choropleth_core.js's repaintDateForStyleSwap, tested, before cycle 01 ran. See finding 02 and docs/map-reviews/README.md's "Measuring" section.

New this cycle: the Boundaries tier follows the basemap, not the provider rows

SNOW-891 changed what scopes the six Boundary layers (regions-line, regions-label and their L1/L2 equivalents). They used to be filtered by which bulletin providers were switched on — so unticking every provider blanked every outline too, since nothing else was drawing them. They are now filtered by the active basemap's declared country coverage instead (settings.BASEMAP_COUNTRIES), because a national basemap like swisstopo or ign_plan renders nothing outside its own country, and an outline drawn past that edge described ground no tile covers. The danger fill is untouched by this — it still follows the provider rows, exactly as before. See docs/decisions/boundaries-follow-the-basemap.md, and finding 09 for the fetch-side cost this introduced.

03

The trick that makes the season scrubber instant

Separate the shape of a thing from what is currently true about it.

Dragging the scrubber recolours all 149 regions for a different day. Naïvely, that is a request per day and a re-upload of every polygon. It is neither.

MapLibre lets you attach a small bag of values to a feature beside the geometry, without touching the source — feature-state. The fill layer's colour expression reads that bag. So the geometry is uploaded to the GPU exactly once, and changing a day is 149 assignments into a side table.

This is a genuinely good decision and it pays for itself twice: it is why the scrubber feels native, and it is why the whole season fits in 40 KB.

It has one sharp edge, and the codebase has been cut by it. Feature-state lives with the source. Destroy the source — which is what a basemap swap does — and every region falls back to "no rating" and the map goes grey. So every style change must trigger a full repaint from whatever day is currently displayed. That is a real coupling between two features that otherwise have nothing to do with each other, and it is the reason a basemap picker is 500 lines rather than 50.

The compensating design

Danger colours are painted opaque, with transparency pre-blended into the colour by choropleth_core.js. A translucent fill would blend with whatever basemap is underneath, so the same rating rendered as five different colours across five basemaps. On a safety product that is not a cosmetic bug.

04

Where the code lives, and the one rule that governs it

79 first-party files, no bundler, no import statements. Load order is the dependency graph.

Browsers offer two ways to load a script. Modules declare their dependencies with import and each gets a private namespace. Classic scripts — the older form — all share one namespace, and a name declared in one file is visible in every file that loads after it.

Snowdesk uses classic scripts throughout. In practice these 79 files behave like a single file that happens to be split across 79 tabs: a variable declared in map_state.js is simply in scope by the time map.js runs. There is no import graph to read. The graph is the order of <script> tags in the template.

For a reader coming from a language with real modules, the closest analogue is a C build with no headers, where the compiler concatenates translation units in the order given and every symbol is global. The consequence is the same: correctness depends on order, and order is not checked by the language.

Two things stop this being reckless. The template's order and the test harness's order are asserted against each other by a Python test, so adding a file in one place and forgetting the other is a red build rather than a map that silently stops booting. And a second linter, js-globals-lint, fails on any read of a global name that nothing anywhere assigns.

That second linter exists because of a real bug, and it is worth knowing as a cautionary tale. One module read window.MAP for its entire life. map.js declares a bare let MAP — which lands in the shared scope but not on the window object. So the read returned "undefined" every time, forever, and every guard around it silently took the "no map yet" branch. Nothing threw. Nothing logged. The feature just never worked.

Files outside the bundle

Modules loaded from their own partials can't rely on being after map.js, so they reach shared state through an explicitly published object, window.snowdeskMapState. It is frozen, so a typo throws instead of returning undefined. Knowing which of the two routes a file is allowed to use is the single most load-bearing piece of tribal knowledge in this codebase.

05

How 75 files that can't call each other manage to co-operate

A message bus, and a rule that each fact has exactly one writer.

Without imports there is no clean way for the calendar to call into the scrubber. So the files broadcast instead. The browser's own event system is used as a publish/subscribe bus: anyone can fire a named message at the document, anyone can listen for it, and neither side needs a reference to the other.

The important discipline layered on top is one writer per fact. "Which day is shown" is the fact most things depend on. Three surfaces can change it — the scrubber, the calendar, the timelapse — but only one function commits it. The calendar does not write the URL or repaint anything; it fires snowdesk:scrub-to, and the scrubber's commitDate does the work. Everything downstream then hears one message, snowdesk:date-changed.

That is the right call, and the reason is stated plainly in the docs: two surfaces writing the URL is two places for the URL and the painted map to drift apart.

MessageFired byWho reacts
snowdesk:scrub-tocalendarthe scrubber — the only committer
snowdesk:date-changedthe scrubber, oncechoropleth repaint · bulletin boundary refetch · weather re-projection · the "read the bulletin" link

snowdesk:placement-focusthe pin-placement flowshides every overlay so you can see the ground
snowdesk:map-readymap.js, on first paintdismisses the app launch screen

The same pattern solves a second problem. Twelve surfaces float over the map — panels, menus, popups, a help tour — and only one is ever meaningful at once. Rather than each one knowing about the other eleven, every surface registers a name plus "are you open?" and "close yourself" with a small registry, and calls "I'm opening" before it appears. The registry closes the rest.

This replaced pairwise wiring that covered three of the fifteen possible relationships between six surfaces — each remembered by whichever ticket added the newest one. A test now runs the whole matrix, so a surface that forgets to register fails there rather than in production.

The honest downside

A message bus makes call sites unfindable. You cannot ask your editor "who calls this?" — you have to grep for a string. The codebase compensates with unusually thorough comments, which is a real cost paid to buy a real benefit; see finding 07.

06

The server side is deliberately boring

Plain Django views returning JSON. No REST framework, no serialisers, no GIS extension.

Every endpoint the map talks to is a function that takes a request and returns a JsonResponse. Region boundaries are stored as JSON columns rather than in PostGIS, and the one geometric operation the request path needs — "which region contains this point?" — is forty lines of ray-casting in pure Python.

Measured against this checkout on a warm cache, the page itself renders in 30 ms on 6 queries — up from cycle 01's 8 ms / 4 queries, and still not the interesting part of the page. The two extra queries are not the map's: they are apps/public/banners.py's new admin-managed site banners, which run a lookup on every page, map or not. The map's own render cost is unchanged.

Two details in that table are worth stealing. The ratings payload encodes danger as a single integer per region — {"2026-02-16": {"CH-4115": 3}} — which is why a seven-month season is 40 KB rather than a megabyte of repeated strings. And the bulletin-boundary endpoint varies its cache header by date: a day old enough that no provider will revise it is served immutable for a week, which is also the signal the offline service worker uses to decide the response is worth keeping.

regions.geojson's 72 ms above is the cold, cache-miss cost — it now sits behind cache.get_or_set keyed on country (closed finding 06), so every request but the first per country per day pays close to nothing. /api/area-content/ is new this cycle (SNOW-953): one bbox in, the micro-regions and public weather locations it touches out, day-free and memoised for a day, replacing a client-side scan of every loaded country's outlines for the same answer.

The bulletin-boundary endpoint used to return the whole season in one response. Once the historical archive landed, serialising every day's dissolved geometry at once pushed the web worker past its 512 MB memory limit. It now serves one day, and the client memoises per date. Worth naming out loud: the failure mode of "just send everything" scales with your archive, so it arrives long after the design decision.

07

Testing, and the rule that keeps it affordable

Three layers, and putting a test in the wrong one is treated as a defect.

The project's stated rule is to work top-down and stop at the first layer that can hold the assertion. Anything reachable from Django's test client is a Python test. Anything a browser-side module does that a simulated DOM can observe is a JavaScript unit test. Only what genuinely needs a real browser — WebGL, the service worker, real clipboard and passkey ceremonies — is an end-to-end test.

The third layer is capped at roughly a dozen tests, and the cap is enforced by a linter that also fails any test over 40 lines or any test file that doesn't name a real manual scenario. That is unusual, and it exists because the line was breached twice: a deliberate cut to 110 browser tests was back up to 280 within sixteen days, because every UI ticket dutifully bundled one and nothing said stop.

The middle layer is where the real coverage is: 179 files, 64,554 lines — up from 157/52,704 at cycle 01, growth roughly proportional to the 47 commits and the new offline-downloads surfaces this cycle covers. To make it possible at all, a harness reads the map's files off disk and evaluates them together in one function scope — because the standard import machinery would give each file a private namespace, and every cross-file reference the browser resolves happily would become an error.

Read this as a design signal

Needing a bespoke harness to reproduce your own loading model is the clearest evidence of what the no-modules choice costs. It works, it is well documented, and it is the kind of thing that is cheap to keep and expensive to acquire — but it is a permanent tax on every new test file.

08

Review — what holds up

The parts a sceptical reader should be told about before the criticism.

  • ✓

    The server is genuinely fast. 4 queries and 8 ms for the heaviest page on the site, with a monitored query-count budget to stop that drifting.

  • ✓

    The payload is already handled. 3.0 MB of source becomes 345 KB gzipped on the wire, because the deploy minifies first-party JS in place before hashing. Two-thirds of what remains is MapLibre itself. If someone raises "you ship unminified JavaScript", they are reading the repository, not production.

  • ✓

    Client-side security posture is clean. One assignment of raw HTML in 8,360 lines, into an attribution string that is server-controlled, with the reasoning written next to it. User-supplied names go in as text everywhere.

  • ✓

    Extracting pure logic works and is already a habit. Twenty-one *_core.js modules now hold the maths — the choropleth palette, the calendar grid, tile arithmetic, elevation profiles, and this cycle's new country_load_core.js — and every one of them is unit-tested without a map at all.

  • ✓

    Four static guards now, each encoding a real production bug or its whole class. Design-token drift, unassigned globals, untranslated strings in JavaScript — and, new this cycle, tsc --checkJs over twelve files via JSDoc types (closed finding 03), the first GENERAL defence the browser side has had rather than one more bug-specific script.

  • ✓

    Boot failure is compartmentalised. The three startup fetches run in parallel and each carries its own error handling, so one dead endpoint degrades one feature rather than taking the map down. That came from an incident, and the comment says so.

Boot now fetches season ratings for every basemap-covered country, whether or not a visitor asked for it

SNOW-957Todo — open question

static/js/map.js:6228–6234 · static/js/country_load_core.js:76–92 planCountryFeeds

SNOW-891 (merged this week) fixed a real bug: unticking every bulletin provider used to blank every Boundary outline too, because nothing else drew them. The fix correctly re-scopes the six Boundary layers to the active basemap's declared country coverage (docs/decisions/boundaries-follow-the-basemap.md) instead of the provider rows. But the boot loop that decides what to fetch changed with it: bootCountries is now the union of boundaryCountryCodes() (all four, on the default openfreemap_liberty style) and whichever providers the visitor has enabled (CH/SLF only, by default). Every code in that union goes through ensureCountryLoaded, and planCountryFeeds has no branch for "fetched only for its outline, no provider wants its bulletins" — so it returns ratings: 'fetch' regardless.

The practical effect: on the default deployed configuration, every first-time visitor now fetches L1 + L2 + L4 boundary geometry and the season ratings payload for France, Austria and Italy, in the background, on every visit — work the pre-SNOW-891 boot loop only did once a visitor's provider row for that country was already on. Confirmed this is not a paint bug first: applyCountryFilters (map.js:3687) keeps the danger fill scoped to the provider filter separately from the basemap-scoped boundary filter, so FR/AT/IT never show colour nobody asked for — this is purely an avoidable background fetch. The decision doc that introduced it says so itself: "Whether the ratings leg should be skipped for a country no provider claims is a separate, measurable question," left open when SNOW-891 shipped.

Suggested fixGive planCountryFeeds a way to tell "loaded for the basemap" apart from "loaded because a provider wants it", and return ratings: 'skip' for the former. Scoped as SNOW-957, which stays at Todo rather than Ready for dev: whether the existing toggle-handler branch that back-fills ratings when a provider is switched on later (map.js:5880–5893) already covers a country that skipped them at boot, or needs its own change alongside this one, has not been traced end-to-end and is named as the open question in the ticket.
