### Where the gap comes from

It is **not** GitHub Actions, and **not** dev/transitive deps that the local
audits exclude — I explicitly audited every PEP 735 group and the full npm
tree. The gap is **stale entries in GitHub's own dependency graph.**

Evidence — `GET /repos/hugorodgerbrown/snowdesk-data-pipeline/dependency-graph/sbom`
(generated `2026-07-30T20:44:34Z`, `"Tool: dependabot"`):

| Ecosystem | Entries in GitHub's graph | Reality |
|-----------|--------------------------|---------|
| `pkg:pypi` | **333** entries / **170** distinct names | `uv.lock` has **170 packages, 170 distinct names — exactly one version each** |
| `pkg:npm` | 512 entries / 475 names | matches `package-lock.json` (564 entries); multi-version names are legitimate nested deps |
| `pkg:githubactions` | 8 | matches `.github/workflows/` |

163 of the 170 Python package names appear **twice** in the graph: once at
the `uv.lock` version, and once at an **older version that is nowhere in the
repository**. 61 names carry a version not present in `uv.lock`, e.g.:

```

These are pre-Dependabot-bump versions. `cryptography 48.0.1` is precisely

### What to do about it

The alerts are **noise, not exposure** — but 28 phantom alerts is exactly
the condition under which a real one gets missed. Force GitHub to re-resolve
the graph:

1. Open the Dependabot alerts UI and confirm the reported *manifest* and
   *version* for two or three alerts (e.g. Pillow). If they say `uv.lock` /
   `12.2.0`, the stale-graph diagnosis is confirmed.
2. Push a commit that touches `uv.lock` (the next weekly Dependabot group PR
   will do it) — this normally triggers a full re-parse and evicts the old
   snapshot.
3. If they persist, disable and re-enable the dependency graph in
   *Settings → Code security*, which forces a rebuild. Failing that, this is
   a GitHub Support issue against the `uv` ecosystem parser.
4. Do **not** bulk-dismiss. Dismiss individually only after confirming the
   cited version is absent from `uv.lock`.

**Location:** `package.json:12` (`"sharp": "^0.34.0"`), `package-lock.json` → `node_modules/sharp` @ `0.34.5`
**Advisory:** GHSA-f88m-g3jw-g9cj (CVE-2026-33327, CVE-2026-33328, CVE-2026-35590, CVE-2026-35591)
**Severity:** upstream **high**; **Medium here** (see reachability)
**CWE:** CWE-1395 (dependency on vulnerable third-party component)
**Installed:** 0.34.5 · **Fixed in:** 0.35.0 (latest 0.35.3) · **Scope:** `devDependencies`
**Evidence:**
```
sharp  <0.35.0

CVE-2026-35590, CVE-2026-35591 — GHSA-f88m-g3jw-g9cj

**Reachability in Snowdesk:** `sharp` is `require()`d only by

#### M3 — CI dependency auditing has two blind spots
**Location:** `.github/workflows/security-audit.yml:89-101`; `tox.ini` `[testenv:audit]`
**CWE:** CWE-1104
**Evidence:** Both the tox env and the workflow export with `--no-dev`:
```yaml
# .github/workflows/security-audit.yml
- name: Export locked dependencies
  run: >-
    uv export --frozen --no-dev --no-emit-project --no-hashes
    --format requirements-txt --output-file /tmp/requirements-audit.txt
- name: Audit dependencies for known CVEs
  run: pip-audit -r /tmp/requirements-audit.txt
```
`--no-dev` drops all five PEP 735 groups (`test`, `type`, `lint`, `sast`,
`e2e`), reducing the audited set from **169 packages to 65**. Every
advisory found in this audit's Python scan (`mcp` ×3) lives in the
excluded 104. Separately, `npm audit` appears **nowhere** in
`.github/workflows/` — `npm ci` runs in `e2e.yml:115` and
`lighthouse.yml:95`, but nothing ever audits the result. The `sharp` and
`brace-expansion` advisories have therefore never been surfaced by CI.
**Impact:** The build/test/lint toolchain runs with repository checkout and
`GITHUB_TOKEN` in scope; a compromised dev dependency is a credible CI
supply-chain path, and CI is currently blind to it. Auditing only the
runtime set gives false assurance.
**Recommendation:** Keep the runtime audit as the **blocking** gate
(deploy risk) and add a **non-blocking** full-set job so tool-chain CVEs are
visible without turning CI red on an unfixable transitive:
```ini
# tox.ini — new env, alongside the existing [testenv:audit]
[testenv:audit-all]
description = Advisory-only CVE check across every dependency group
skip_install = True
allowlist_externals = uv
deps = pip-audit
commands =
    uv export --frozen --all-groups --no-emit-project --no-hashes \
        --format requirements-txt --output-file {envtmpdir}/requirements.txt
    - pip-audit --requirement {envtmpdir}/requirements.txt
```
and add to `security-audit.yml`:
```yaml
- name: Audit JS dependencies (advisory only)
  run: npm audit --audit-level=high || true
```
Also add `npm` to `.github/dependabot.yml` (currently only
`github-actions` and `uv`; the file states npm is "out of scope"). Security
*alerts* fire for npm regardless, but without a version-update ecosystem
there is no automated PR path to ever fix them.

#### L2 — `brace-expansion` 1.1.16 ReDoS/OOM (dev-only, no clean fix path)
**Location:** `package-lock.json` → `node_modules/brace-expansion` @ `1.1.16` (`"dev": true`)
**Advisory:** GHSA-mh99-v99m-4gvg · CVSS 7.5 · CWE-400, CWE-770
**Installed:** 1.1.16 · **Vulnerable range:** `<=5.0.7` · **Fixed in:** 5.0.8 (latest 5.0.9) · **Scope:** `devDependencies`
**Evidence:** Chain, entirely under Lighthouse CI:
```
brace-expansion@1.1.16 → minimatch@3.1.5 → glob@7.2.3 → rimraf@3.0.2
                       → chrome-launcher@0.13.4 → @lhci/cli@0.14.0
```
`npm audit` reports this as 7 "high" findings; they are **one** advisory
counted once per link in the chain. Every node is `"dev": true` — the npm
tree has `prod: 1` (the root package) and `dev: 563`.
**Impact:** Denial of service (unbounded expansion → OOM) against a process
that calls `braceExpand` on an attacker-controlled glob. In Snowdesk the
only caller is Lighthouse CI's file globbing over repo-controlled paths, on
a developer machine or an ephemeral CI runner. Worst case is a crashed
`npm run lh`. Never reaches production or a browser.
**Recommendation:** Low priority; `npm audit fix --force` proposes
`@lhci/cli@0.3.3`, a catastrophic downgrade that `package.json`'s own
`comments.overrides` block already warns against (SNOW-440). The consistent
fix is another entry in the existing `overrides` block, but note that
`minimatch@3` expects the 1.x API and npm's advisory range does not exempt
the `maintenance-v1` line (1.1.18), so only a `^5` override reads as clean:
```jsonc
// package.json — extend the existing "overrides" block
"overrides": {
  "tmp": "^0.2.6",
  "uuid": "^11.1.1",
  "cookie": "^0.7.0",
  "brace-expansion": "^5.0.9"   // verify: npm run lh must still pass
}
```
Then `npm install` and confirm `npm run lh` still completes. If it breaks,
accepting this advisory is entirely reasonable — document it in the
`comments.overrides` note alongside the existing SNOW-440 rationale.

#### L3 — First-party GitHub Actions pinned to mutable major tags
**Location:** `.github/workflows/` — 20 call sites across 8 files
**CWE:** CWE-829 (inclusion of functionality from an untrusted control sphere)
**Evidence:** Third-party actions are SHA-pinned, first-party are not:
```
ci.yml:88            uses: actions/checkout@v7            # mutable tag
ci.yml:91            uses: actions/setup-python@v7        # mutable tag
e2e.yml:110          uses: actions/setup-node@v7          # mutable tag
e2e.yml:118,128      uses: actions/cache@v6               # mutable tag
lighthouse.yml:132   uses: actions/upload-artifact@v7     # mutable tag
lighthouse.yml:89    uses: astral-sh/setup-uv@c771a70e…   # v9.0.0  ✅ SHA
security-audit.yml:143 uses: gitleaks/gitleaks-action@e0c47f4f… # v3.0.0 ✅ SHA
dependabot-auto-merge.yml:33 uses: dependabot/fetch-metadata@25dd0e34… # v3.1.0 ✅ SHA
```
This contradicts the policy `.github/dependabot.yml` documents for itself:
*"Third-party actions in `.github/workflows/` are pinned to immutable commit
SHAs … so a moved upstream tag cannot execute new code in CI unreviewed."*
The stated rationale applies equally to `actions/*` — the `v7`/`v6` tags are
branch-like refs that GitHub's own release process moves.
**Impact:** If the `actions` org were compromised (or a maintainer account
taken over), a moved `v7` tag would execute new code in every Snowdesk
workflow without review. This is the `tj-actions/changed-files` (CVE-2025-30066)
attack shape. `GITHUB_TOKEN` is well scoped (`contents: read` on all but
`release.yml` and `dependabot-auto-merge.yml`), which bounds the blast
radius, so Low rather than Medium. Trusting GitHub-owned actions is a
defensible position — but it should be a *stated* exception, not silence.
**Recommendation:** Either SHA-pin the five `actions/*` entries with a
`# vX.Y.Z` comment (Dependabot's `github-actions` ecosystem is already
enabled and will keep them current, exactly as it does for the third-party
pins), or add an explicit note to `dependabot.yml` recording that
GitHub-owned actions are deliberately tag-pinned and why. No `uv`/`npm`
command applies.

#### L4 — The security-gate workflow installs its own tooling unpinned
**Location:** `.github/workflows/security-audit.yml:88` and `:120`; `tox.ini` `[testenv:audit]` `deps = pip-audit`
**CWE:** CWE-1104
**Evidence:**
```yaml
- name: Install pip-audit
  run: pip install pip-audit          # unpinned, resolved at run time
...
- name: Install tox
  run: pip install tox tox-uv         # unpinned, resolved at run time
```
**Impact:** The job whose purpose is to detect supply-chain problems pulls
three packages straight from PyPI at unpinned, unhashed, latest-at-run-time
versions. A compromised release of any of them executes inside CI. Low
because the job holds only `contents: read` and no deployment secrets.
Note this is also a consistency gap: every other tool in the project is
pinned through `uv.lock` per
`docs/decisions/tox-envs-install-from-uv-lock.md`, and `[testenv:audit]`
is the one env that opts out with a bare `deps =`.
**Recommendation:** Move `pip-audit` into a PEP 735 group so it is pinned by
the lock like `semgrep` already is, and convert `[testenv:audit]` to the
`uv-venv-lock-runner` used by every other env:
```bash
uv add --group audit pip-audit    # then set dependency_groups = audit in [testenv:audit]
git add pyproject.toml uv.lock
```
and change the workflow to `run: tox -e audit` (matching how the `sast` job
already delegates), so CI and local runs install identical versions.

lockfile pins 6.0.7, and the fix version for all three Django advisories is
`5.2.16, 6.0.7`, so the deployed code is not affected.

## Suppressed findings

- **`npm audit`'s 7 "high" → reported as 2.** `minimatch`, `glob`, `rimraf`,

- **Pillow, PyJWT, Django, pyasn1, starlette, click, pydantic-settings.**
  Not reported as findings — the pinned versions are patched. Tabulated

- **npm `overrides` for `tmp`/`uuid`/`cookie`.** Verified working:
  `tmp@0.2.7`, `uuid@11.1.1`, `cookie@0.7.2` are all patched in the
  installed tree. No finding.
- **`dependabot-auto-merge.yml` holding `contents: write` + `pull-requests: write`.**
  Triggered by `pull_request`, not `pull_request_target`, and gated on
  `if: github.actor == 'dependabot[bot]'`; fork PRs get a read-only token
  and no secrets. Correctly built — no finding.
- **`release.yml` holding `contents: write`.** Required to create tags and
  releases; scoped to that one workflow. No finding.

## Out-of-repo recommendations

- Grant the audit token `security_events: read` (or run `gh auth` locally)
  so the Dependabot alert list can be enumerated directly — this audit had
  to infer it from the SBOM.
- Confirm in *Settings → Code security* that Dependabot alerts and the
  dependency graph are both enabled, and that grouped security updates are
  on for the `uv` ecosystem.
- Render dashboard: confirm the three production services build from the
  committed `uv.lock` (`uv sync --frozen`) and never resolve fresh at deploy
  time — otherwise the audited set is not the deployed set.

## Recommendations beyond fixes

1. **Rebuild the dependency graph first, fix CVEs second.** Nothing in the
   current lockfiles is urgent; the 28 phantom alerts are the actual risk
   because they train the team to ignore the alert badge.
2. **Split the audit gate: blocking on runtime, advisory on everything else**
   (M3). Keeps deploys honest without CI going red on an unfixable
   transitive of a linter.
3. **Add `npm` to `.github/dependabot.yml`.** Alerts already fire for it;
   without the ecosystem there is no automated remediation path, which is
   how `sharp` sat at 0.34.5.
4. **Pin `pip-audit` through `uv.lock`** like every other tool (L4), and
   have the workflow call `tox -e audit` rather than reimplementing it — the
   workflow and the tox env are currently duplicated and can drift.
5. **Record a dev-dependency CVE policy** in `docs/`: dev-only advisories are
   triaged for reachability and may be accepted with a written rationale
   (the `package.json` `comments.overrides` block is already a good example
   of this practice — generalise it).
